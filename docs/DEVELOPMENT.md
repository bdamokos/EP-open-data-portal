# Development

Use the Node version in `.nvmrc`. The frontend entry is `src/main.tsx`. Navigation uses query parameters at the application root. Static serving covers only the root page, `index.html` and `assets/`; other paths return 404.

The unfinished amendment catalogue is hidden by `publicAmendmentsEnabled` in `src/publicFeatures.ts`. This gates its main navigation, MEP tab and document/dossier links. Old catalogue URLs fall back to Members, and old MEP amendment-tab URLs to Latest speeches. The amendment components, API, parsing, indexing and stored data remain intact; motion outcomes and original/joint/adopted wording comparisons remain public.

The server binds to loopback by default and has no accounts. A reverse proxy must overwrite forwarded headers before `TRUST_PROXY=true` is enabled. Site routing, access controls, host configuration and credentials belong outside this repository.

## Local configuration

SQLite must include FTS5: use Node.js 22.16 or 24+; earlier releases and Node.js 23 do not provide it. `.nvmrc` specifies the project version.

For question and legislative history, enable a local activity index:

```sh
mkdir -p var/cache var/index
ODP_CACHE_DIR="$PWD/var/cache" ACTIVITY_INDEX_DIR="$PWD/var/index" ACTIVITY_INDEX_ENABLED=true npm start
```

After startup index preparation, one dedicated worker thread hosts both leased source-writing loops. The HTTP thread opens read-only activity, press and corpus connections. Writer requests acquire grants from the HTTP thread’s shared admission queues; fetching and body parsing stay in the writer thread. A crash releases its grants and restarts it with exponential backoff (one second to one minute); database leases remain authoritative. Shutdown aborts both loops, drains their current work and releases leases, with a 30-second termination deadline. The writer isolate has a 512 MiB old-generation heap limit; SQLite, buffers and nested extraction threads use additional memory. Committed revision notices wake plenary warming after a new generation; reader caches and Following/amendment readiness continue to read persisted WAL revisions. Cold sitting reads forward coalesced ID tuples to the writer collector’s high-priority queue, with at most 512 IDs per batch and one unacknowledged batch. Projection backfills and the lease-scoped member-profile cache stay in the writer.

The indexer starts with bounded requests and retains its progress. Initial coverage is partial and is shown in the interface. Do not run two processes against the same index directory. Cache and index data stay outside Git. `.env.example` lists the available settings; load environment variables through your shell or service manager.

Boolean settings accept `1`, `true`, `yes`, `on` and `0`, `false`, `no`, `off` (case-insensitive); other nonempty values fail with the setting name. Worker flags are checked when accessed or started; directory and bounded job settings are read when their service is first created. Relative paths resolve from the working directory. `JSON_RESPONSE_LIMIT_BYTES` caps supported JSON responses (default 5242880 bytes).

For full-text search, add `CORPUS_ENABLED=true CORPUS_DIR="$PWD/var/corpus"`. A background worker stores speech texts and question/answer texts in `corpus-v1.sqlite`, searchable through `/api/corpus/search` and joined read-only to the activity index; `/api/corpus/status` reports coverage. It pauses at `CORPUS_MAX_DISK_MIB`. See [Public data sources](PUBLIC_DATA.md#full-text-corpus).

When `ODP_CACHE_DIR` is set, portraits are also cached on disk in its `portraits-v1` subdirectory. Use one cache writer per directory and keep the cache mount when replacing a container.

The serving process prewarms English agenda week lists and multilingual source records for the latest four plenary weeks, counting sitting weeks across recesses. It starts after HTTP listening and roster readiness and uses the shared background request admission. After preparing each latest-week batch, the scheduler yields before continuing. Completed batches wake within one hour, including recesses and year boundaries, to discover newly published linked details. Unavailable sources retry hourly, and roster readiness is checked separately without source reads. Agenda sources live in `plenary-agendas-v1`, bounded to 32 MiB and 160 records with least-recently-used eviction; older cache locations remain readable. Assembled lists share the existing 48-entry/64 MiB disk view cache. Latest-week item details and linked public sources are prepared in small serial batches using their existing caches and request budgets. Completed-week agenda sources have no age-based expiry after one post-week observation, including across restarts and consumers; current and future agenda sources have a minimum one-hour lifetime. Complete historical week views do not expire by age; active week lists use one hour at the origin and CDN. Preliminary lists use one minute, and unresolved latest selections use five minutes; transient failures remain uncached. Date/index changes can still rebuild the response envelope and navigation. Latest selections check the shared calendar and bind their view key to its content, so a newly listed sitting replaces an older latest week without rechecking fixed historical agendas. Missing or transient observations remain retryable gaps, and explicit maintenance refreshes remain possible. An actual changed agenda publication advances a small persisted cache revision, invalidating retained source projections and views without polling; unchanged source content does not advance it. Before changing retained source bytes, publication writes a pending revision marker. Each unsaved agenda stays pending until its own identical or changed retry is retained; another agenda cannot commit that observation. A committed revision is issued only after all pending sources succeed. Derived views remain memory-only while publication is pending or their revision changes during loading. A restart after an interrupted publication creates a new view namespace for the bytes actually retained. If the pending marker cannot be saved, source files stay untouched and fresh data remains available in memory. Legacy-file migration preserves the retained observation in the bounded directory before removing aliases; cleanup failures keep new data in memory until migration can complete, without creating an upstream failure. Historical agenda corrections are not discovered by routine age checks; retrieval dates retain the original observation.

## Data recovery and request pacing

Run `npm run data:audit -- --reconcile` in the service environment to inventory both serving and working queues, retained gaps and exact question/answer distribution URLs without starting a writer. Alternatively supply `--index FILE --corpus FILE --press FILE`. Missing databases or tables are reported as unavailable. A queue is evidence of ownership; compare successive reports and service settings to establish progress. Keep reports outside Git.

Save a baseline with `node server/data-gap-audit-cli.mjs --reconcile > /absolute/path/baseline.json`, then add `--baseline /absolute/path/baseline.json` on later runs. Comparisons list resolved and newly missing exact identities; the question-file denominator has a digest so changed source scope is visible. Failure classes separate throttling, transient errors, source absence and source/parser problems without declaring a missing record permanently unpublished.

`ACTIVITY_INDEX_RECOVERY_MODE=backfill` admits up to 25 already-due durable source gaps per worker iteration, including between daily refreshes. The existing writer, cursors, retry dates, request budget and disk limit still apply. Return to `normal` for the ordinary 25-per-day recovery policy. This mode does not reopen future retries, historical coverage-window labels, completed empty extractions or unsupported parser results.

API requests emit `[odp-throttle]` events and one `[odp-monitor]` JSON summary per minute to the existing service logs. These distinguish HTTP 429, HTTP 503, network failures, route families, recent request starts and local quota headroom. `ODP_REQUEST_MODE=backfill` spaces starts by at least 750 ms (80 per minute, 80% of the published rate), leaving reader capacity within the shared 500-per-five-minute ceiling. It slows after 429/503 and cautiously recovers after successful responses. `steady` starts at 1500 ms for periodic updates; the default `normal` preserves the existing unpaced rolling allowance. Every mode honors the same rolling ceiling, reader reserve and server pauses. Select the mode in runtime configuration; logs measure ordinary useful work, with no separate quota probes. Observations reset on process restart, and process-local limits assume one application source writer.

## HTTP caching

Anonymous, stateless API reads use a six-hour CDN lifetime; activity and speech lists use one hour. Dossier press-release lists use 15 minutes once following has started, every feed read succeeded and the procedure file was read fresh. Positive speech/document reading responses dated at least 14 days ago use 24 hours, except unanswered questions, whose answer links can still change. Answer age comes from the selected answer, not its parent question; unknown dates keep six hours. Browsers revalidate API responses. Partial index and corpus coverage remains an explicit snapshot, with source retrieval dates preserved; background retries do not by themselves invalidate saved observations. Source refresh schedules are independent and unchanged: CDN lifetimes describe when a shared cache checks this server, not the maximum age of upstream data.

Health, progress, diagnostic failures, stateful speech statistics, speech clouds and topic trends, non-read methods, errors, and temporary unavailable/stale/refreshing responses use `no-store`. Directory responses also use `no-store` until committee memberships and optional committee details finish loading, including conditional reads; completed directory snapshots retain the six-hour CDN lifetime. Upstream freshness state is retained through reading and legislation projections. Successful portraits use up to seven days at the CDN and one day in browsers, capped by the saved image's existing source expiry, with content ETags and Origin variation for conditional reads. HTML and source maps revalidate: a map can change without changing its script's fingerprint. Vite's build manifest identifies fingerprinted assets for one-year immutable caching; other assets use five minutes.

The application sends separate `Cache-Control` and `CDN-Cache-Control` headers. A gateway must preserve the approved public policy and keep its own errors, private routes and legacy routes uncached. A CDN needs explicit eligibility for JSON and extensionless portraits, must respect origin `no-store`, and must retain the full query string and Origin in its cache key. Frontend JSON API GETs, including prefetches, carry `v=<API_VERSION>`; portraits use their independent `v=<PORTRAIT_VERSION>`; page and share URLs do not. The server validates and removes this parameter before endpoint parsing. Only the current endpoint version can receive a public CDN policy. Portraits also accept the current JSON API version for older clients. Missing versions receive CDN `no-store`; different versions return HTTP 409 `api_version_mismatch` with the current `apiVersion` in the error, and invalid or repeated values return HTTP 400. Errors use browser and CDN `no-store`. A version mismatch replaces the app with one localized, accessible reload notice; its button reloads the current URL without automatic retries. CDN eligibility rules must require `v` for API GETs and respect origin cache headers. Hosting-specific configuration belongs outside this repository.

`server/api-version.mjs` owns the monotonic `API_CONTRACT_REVISION` and wrapped `API_VERSION` (1–999). Registry keys remain revisions; requests keep the existing `v` parameter. Bump the revision only when an API response contract actually changes, including response semantics, and never for a commit, build or deploy alone. Update the relevant endpoint `*_VERSION` and run `npm run api:bump` to append the current digest and reconcile branch entries after main without replacing recorded main mappings. Use `-- --force` once for semantic-only changes with an unchanged digest. See CONTRIBUTING.md for merge/rebase conflicts. `node --test server/api-version.test.mjs` checks the endpoint inventory digest; CI also checks recorded history against its immutable baseline. These checks never bump automatically. Data refreshes use the existing cache lifetimes.

Portraits render their real image URL immediately, using native lazy loading for the wall and eager loading for selected profiles. Their independent `PORTRAIT_VERSION` changes only when the image endpoint changes; unrelated API updates preserve browser/CDN cache keys. Image content keeps its checksum ETag and bounded freshness, so updated photos revalidate normally. A failed native request shows a silhouette without automatic retries: image error events do not expose HTTP retry headers. Successful native loads do not fetch blobs or wait for JavaScript intersection observers. No bulk endpoint or roster download is added.

## Client request budgets and busy responses

ODP admission uses the specification's 500 requests per five minutes as one conservative API-wide rolling window, shared by foreground readers, feeds and both source writers through the HTTP thread’s admission queue. A real network attempt consumes one start, including retries; cache hits, shared readers and cancelled queued jobs consume none. Background work may use at most 80% (400 starts); the remaining 100 are reserved for visitors and other foreground reads. The two-operation cap and one-background admission cap protect resources independently of that quota. Shared foreground joins can use reserved quota without bypassing background admission. An in-flight foreground request gaining a background owner is counted before further background admission. If its last reader leaves while another background operation is active, its retained GET is rescheduled to release foreground capacity; the replacement consumes another quota start. A quota wait holds no connection, and interactive admission remains bounded at ten seconds with a retry hint for the next available start. Valid server cooldowns can exceed the reader's deadline; background owners retain their bounded retry budgets through the pause. Activity-index and corpus 404/410 failures retry after one hour, doubling to a seven-day cap, with a six-hour minimum for sitting outcomes during the correction period and honouring longer upstream retry hints. Recorded activity gaps retain attempts across publication and retry admission; their `failedAt` and `retryAt` status timestamps use ISO UTC strings (`retryAt: null` for non-retryable coverage windows). Transport failures (5xx, 429, timeout and network errors) remain retryable; after eight failures their backoff is one day, honouring longer upstream hints. Invalid or empty documents settle only after three identical content-hash, descriptor and parser-version rejections spanning at least 24 hours, as permanent source issues with descriptor, content hash, parser version and reason retained in the data-gap audit. They do not block collection; unchanged issues are rechecked every 30 days, and changed descriptors reopen them. A retained sibling PDF settles the DOCX task as satisfied by alternative while preserving its source issue. Press failures use capped exponential backoff without an attempt limit; repeated 404/410 over more than seven days use the 30-day cadence. A new RSS observation reopens a failed release. Missing evidence remains an explicit gap until a successful read. The recovery queues keep at most 25 gap tasks and 100 mutable-document refreshes admitted at once, refilling on each worker iteration under the existing request budgets. Persisted dispatch shares give gap and mutable recovery regular turns after eight ordinary tasks, retain adopted-text backfill turns, and give due group-voice jobs one turn after eight core dispatches. Normal and backfill runs both advance the bounded, resumable declared-debate scan. Run one server source writer and one index writer; independent processes do not coordinate their in-memory allowances. Other origins have separate resource pools and cooldowns, with no inherited ODP quota or fixed API pacing. See [Public data](PUBLIC_DATA.md) for source scope.

Vote-result tasks that cannot admit an amendment rebuild retain their saved graph and wait at least 30 seconds before retrying, allowing queued amendment work to free capacity. This local admission delay does not count as a source failure or increase either queue's limit.

Browser GET reads share one deadline across attempts, response parsing and retry waits. Each consumer releases its own subscription on navigation or unmount; the last release cancels unowned transport/backoff after a StrictMode-safe microtask. Signal-less reads and started prefetches retain useful shared cache work. Invalidation transfers live subscribers to the replacement read. Upstream-backed directory, speech lists, activities, speech statistics, speech/document/source reading, media metadata and reference routes use 35 seconds: the server's 30-second HTTP budget already includes admission to the shared upstream queue, with five seconds left for transport. Profiles retain 40 seconds, speech context 60 seconds and motion comparison 90 seconds; the latter two have a 50-second server budget. Upstream-backed insights (speech clouds, procedure context, topic trends, legislation and participation) and Questions analysis use 35 seconds. Questions covers the 30-second server reader budget plus transport; other local projections—including latest activities, activity-index status, retained transcripts, corpus reads, speech-word/saved/group-voice insights and indexed amendment readers—retain eight seconds. No timeout changes the shared upstream rate limit or adds a writer. Agenda selections render their cached heading and exact document links immediately while detail reads settle. An open document keeps the member context chosen when it opened, so later contributor enrichment does not restart its text request.

The GET transport exposes error `code`, `status` and `retryAt`. A 503 with `busy`, `upstream_busy`, `odp_rate_limited` or `request_timeout` and a valid retry hint can retry twice, keeping loading visible. It honours the latest of JSON `retryAt`, JSON `retryAfter` and HTTP `Retry-After` (seconds or date), with at least 250 ms between attempts and at most six seconds of backoff. A hinted pause over three seconds surfaces the existing error immediately. Speculative prefetches do not retry unless a foreground reader joins the pending read. Aborts, invalidation and the original route deadline cancel backoff; failed refreshes retain saved data.

The HTTP process samples event-loop delay every 20 ms. Every 30 seconds it logs one compact `[event-loop-delay]` line if p99 reaches 100 ms or max reaches 250 ms, then resets the histogram. Request-budget timeout logs include the current window's p99/max delay in milliseconds alongside utilization and upstream queue state. These diagnostics add no public endpoint.

Main-thread SQLite calls taking at least 250 ms emit `[sqlite-slow]` with the store, statement prefix and SHA-256 prefix, elapsed milliseconds and returned/changed rows when available. Bindings and retained text are excluded. Streaming reads measure SQLite stepping time, excluding work between rows. Background runs use a 250 ms log threshold; task iterations use five seconds and include upstream waits. SQLite uses a 2 MiB cache per database, disabled mmap and file-backed temporary storage. Idle ticks use metadata and pending-queue indexes without taking a writer lease; catalogue repair uses a durable queue. Amendment overflow invalidation seeks a partial index of target documents with a present link-version marker; repeated overflow avoids scanning unmarked source bodies, while source refreshes automatically restore eligible index entries.

Motion-week navigation reads a per-sitting decision-presence summary with retained source URLs and retrieval dates. Motion preparation seeks a partial document index. Member activity pages read a small serving-state summary; the diagnostic status endpoint retains the archive-wide aggregates. A refresh failure qualifies a member role only through that exact source’s saved role projection. Unknown authors, speakers and collection windows remain global availability evidence. Saved-member counts, first-publication marks and preview selection use partial activity/answer indexes; only the ten selected activity previews load bodies. Question and answer DOCX metadata is projected by the activity writer, copied with its generation, and removed with its source. Corpus discovery compares small file-manifest signatures with durable acknowledgements, then anti-joins changed files against indexed corpus URLs. Queue writes and acknowledgements commit together, so interruptions resume without rereading source bodies. Language-policy changes revisit manifests; unchanged file manifests remain acknowledged across publication. These projections do not establish complete coverage or discard retained text or language variants.

Container startup automatically prepares SQLite indexes, per-sitting snapshot tables and proof projections for enabled activity and corpus services before opening the HTTP listener or starting background writers. No separate deployment command is required. Use the normal persistent mounts, `ACTIVITY_INDEX_DIR`, `CORPUS_DIR` and disk-limit environment; stop the old container before starting its replacement. Preparation refuses an active writer lease, logs each build stage and final byte counts, checkpoints only its writable database, and skips completed preparation on repeat starts. It makes no upstream requests or generation changes and exits on failure before serving. The question-file preparation stage streams one saved question at a time and logs its source count and build time. Preparation can take 20–30 minutes or longer on a slow shared disk. The image allows a 60-minute health-check startup period; readiness succeeds as soon as preparation finishes and HTTP serving begins. Deployment readiness deadlines must allow this startup work. `node server/migrate-indexes.mjs` remains available for explicit maintenance diagnostics, but is not a deployment prerequisite. Keep deployment configuration and the selected maintenance window outside this repository.

The activity disk cap defaults to 8192 MiB and accepts 64–131072 MiB. Explicit environments override the default. Allow space for retained generations and WAL, not only new indexes. The preparation command checks the configured cap after its commit and truncating checkpoint; temporary sort files and duplicate WAL pages during the build do not trigger the normal worker cap. Normal worker checks count the database, WAL and SHM files. Corpus limits remain independently configured. Amendment pages return HTTP 503 until their current proof projection is initialized.

Run `node server/test-support/slow-read-benchmark.mjs` for source, amendment, question-title and procedure-event query plans and cold SQLite page-read counts. Source metadata, question analysis inputs, title trigrams and procedure event dates are projected on disk by source-write triggers. Startup adds only their empty tables and indexes. The single activity writer fills retained generations in committed batches of at most 32 rows with persisted cursors, yielding after a batch for each retained generation at iteration start and after every eight core dispatches. Readers use the existing source queries until their projection group is ready for the serving generation. Preparation makes no source requests and adds no deployment readiness gate. Retained source bodies and retrieval dates remain unchanged. Observation retention uses indexed slices of 64 records and a trigger-maintained count.

Run `npm run bench:reads` (requires the `sqlite3` CLI) for the offline synthetic read benchmarks. Each scenario records SQLite page fetches, returned rows, full-scan steps and EXPLAIN QUERY PLAN in a JSON result under the system temporary directory; CI prints a comparison table in its step summary. The separate `read-benchmarks` job fails above baseline page fetches × 1.20 + 10, or on a new full scan of a large table. Wall-clock time appears in the summary and is informational. The baseline records the CLI, Node and Node SQLite versions; a SQLite CLI or Node SQLite mismatch fails the gate. CI builds SQLite 3.45.1 from checksum-pinned source. To refresh, run the Checks workflow on the branch, copy the regenerated baseline JSON from the read-benchmarks step summary into a local file, then run `npm run bench:reads -- --update-baseline /path/to/ci-baseline.json` and commit the reviewed diff. Local `--update-baseline` without a file is suitable only with the exact CI toolchain. Add benchmark suites in the small registry in `scripts/read-benchmark.mjs`. Fixtures use fresh connections, 2 MiB caches and disabled mmap, with no downloads or retained caches; page fetches do not measure physical disk reads. The standalone `node server/test-support/remaining-read-benchmark.mjs` also reports historical before/after counts and preparation cost.

```sh
docker build -t parliament-explorer .
docker run --rm -p 127.0.0.1:8790:8790 parliament-explorer
```

The image runs as an unprivileged user and includes only built assets, runtime modules and production dependencies. Tests, fixtures, server declarations, documentation and local state are excluded. The build accepts `NODE_IMAGE` for an immutable base-image reference and `APP_REVISION` for the source label and response header.

CI also starts the built production image with its normal command and health check. To repeat locally, build with `--build-arg APP_REVISION="$(git rev-parse HEAD)"`, then run `node scripts/check-runtime-image.mjs parliament-explorer "$(git rev-parse HEAD)"`. This check disables outbound networking and source writers, uses temporary in-memory data, and verifies health, revision headers and the built frontend entry without publishing a host port.

For persistent data, mount a writable cache directory at `/data/cache` and an index directory at `/data/index`, owned by UID 1000. Extracted document texts in the cache directory are capped by `DOCUMENT_TEXT_MAX_DISK_MIB` (default 256). Retained amendment-list DOCX files sit beside the index in `amendment-docx-v2`, capped by `AMENDMENT_SOURCE_MAX_DISK_MIB` (default 512, range 64–8192); the current term-10 lists need about 80 MiB, growing by a few MiB per plenary week. `AMENDMENT_SETTLE_GRACE_DAYS` defaults to 60 (range 1–3650); the exact boundary remains within grace. The default doubles the next 30-day interval above sampled public language issue lags; current metadata cannot establish a complete correction history. Exact linked sitting dates extend the window, and unknown documentary dates retain weekly byte refreshes. Settled lists receive exact list-detail checks every `AMENDMENT_SETTLED_METADATA_DAYS` (default 90, range 1–3650), queued by the existing daily preparation with normal request admission and backoff. A persisted per-list `metadataCheckedAt` survives restart and parent-feed updates, so fresh expanded observations cannot postpone the exact check. Selected-wording or author-language descriptor changes and missing retained bytes trigger downloads; unused new languages remain metadata only. Missing or unretainable author-language bytes share the weekly retention retry backoff. `lastConfirmedAt` advances only for unchanged selected descriptors and preserves the last good date through changed or unavailable metadata. These dates remain in source records, separate from wording retrieval dates and public responses. The first amendment extraction access imports the former `amendment-docx-v1` cache; eligible records are removed after successful retention. Records retrieved before their declared issue time are discarded; storage failures and budget refusals keep eligible inputs for retry. Retained DOCX reuse requires exact URL, language and declared size, equivalent issue instants when both descriptors publish them, and a valid original retrieval time at or after the current issue time when present. This applies to dated rows from older writers as well as undated imports; an older retrieval requires a new download even if its saved issue time matches. Undated refreshes record the descriptor actually observed and may serve later dated metadata only when their retrieval time qualifies. The writer removes the obsolete publication-binding table on first source-store access; no binding backfill or byte migration is needed. Reuse and migration preserve retrieval timestamps. Wording freshness and normal extraction admission apply the same chronology check, so undated refreshes cannot hide a later republication until the weekly refresh. Set `ACTIVITY_INDEX_ENABLED=true` to enable history indexing. Use only one index writer. The optional full-text corpus (`CORPUS_ENABLED=true`, `CORPUS_DIR`) needs its own persistent directory and disk budget (`CORPUS_MAX_DISK_MIB`); a full term with all languages needs roughly 10–15 GB. It has one leased writer and reads the index without writing to it. Preserve retained data when replacing a container; do not reset generations or bulk-download sources as a release check.

## Member voting API

`GET /api/member-votes/{personId}` projects a positive Open Data person ID over one held plenary `sitting=MTG-PL-YYYY-MM-DD` or Monday `week=YYYY-MM-DD` (`week=latest` by default). Optional parameters are `lang`, `limit` (1–100, default 25), `offset` (0–10000), exact `decision`, `snapshot`, and `positions=all|recorded` (default `all`). Unknown, duplicate and invalid parameters return 400. Exported response types live in `src/MemberVotesTypes.ts`; this endpoint does not depend on the activity index. The member Votes view consumes it.

`GET /api/decision-votes/{decisionId}` reads one exact held decision from the same bounded sitting snapshot. It accepts `lang` and an optional `snapshot`, and returns actual voter IDs, integrity flags, exact amendment/component references and source provenance. Dated groups come from one frozen serving membership generation; missing groups never use current affiliations. Missing membership history withholds the group table, while unknown vote methods withhold the named read. Responses use `no-store`. Amendment readers validate the exact references and indexed facts before joining authors or displaying group totals. Reads start near the viewport; author sentences remain separate from expandable group results and source details.

The version-4 response resolves a concrete `period`, supplies a `snapshotId`, and paginates decisions by date descending, then exact ID. `positions=recorded` includes only actual named positions; `filteredTotal` counts that member projection while `observedTotal` still counts all observed decisions. `pagination.recordedTotal` counts actual recorded positions before either filter and is null when coverage is unavailable. Fresh client visits use All decisions; newly written journeys always include `mv-positions`. Existing journeys with other `mv-*` state but no positions decode as recorded to preserve their pages. `observedTotal` describes that retrieved snapshot, including non-named and non-conducted observations; it is not a term total or participation denominator. Pin subsequent pages with `snapshot`; selection by `decision` searches the full pinned snapshot independently of the visible page and position filter. A retained `week=latest&snapshot=…` resolves its original week without looking up today's latest week. Evicted, expired or mismatched snapshots return 409. Snapshots are shared across members and languages, retained for at most ten minutes, with an eight-entry/32 MiB memory limit.

`coverage` separates catalogue, source pages and declared result/decision children, with failed and incomplete sittings. Expected results come from both the meeting's own children and expanded result parents. Missing records are distinct from an empty successful collection. Repeated or conflicting source pages, bounds, inconsistent identities, missing children and upstream failures prevent complete coverage. Compatible partial decision records add missing fields. Overlapping records that disagree retain each stream's observed alternatives and source pointers in each item's `sourceConflicts` and withhold position, outcome, totals and subject enrichment. `collectionComplete` describes these checks only; publication can change. Sources retain retrieval times, content hashes and stale/refresh flags. Hashes identify retrieved content, not publication timestamps. No mandate eligibility or historical group membership is inferred, and no group percentages are supplied. Attendance is retrieved separately and does not alter this coverage or vote positions.

`subjects` groups by exact vote-result identity over the full bounded period projection. Each group retains source titles, document and agenda IDs, declared/observed decision IDs, and separate source-derived `wholeTextDecisions`; a group outcome never replaces an individual decision. Group `counts.observed`, `counts.filtered` and `counts.page` distinguish known observations from the current page and are not a term census. Unlinked decisions have `subjectId: null`. `resultRelationship` exposes forward and inverse source edges; ambiguous or contradictory parents withhold subject, split and requester enrichment.

Result pages retain bounded roll-call, split and separate-vote requests. `parts` matches exact component references to split requests explicitly owned by the unique result, preserving language-specific XML literals, decoded text, sibling descriptions and request scope. `rollCallRequesters` requires an exact decision `was_motivated_by` edge to a roll-call request owned by that result; narrative request labels cannot bind a requester. Evidence paths identify source URL, content hash and JSON pointer; unavailable wording, relationships and outcomes remain explicit gaps. Source titles are preserved without presentation cleanup. No document body is fetched by this collection.

Votes first read compressed, member-independent per-sitting observations from `activities-v1.sqlite`. The existing leased activity writer discovers held current-term sittings through paged yearly meeting catalogues and collects exact meeting metadata, decisions, named positions, results, agendas and optional chair evidence at background priority under the shared ODP budget. Current-year catalogues refresh every six hours; earlier years refresh monthly. Sitting snapshots refresh every six hours through `sittingConfirmationDay`, then complete observations receive monthly checks. Partial/unavailable observations retry with exponential backoff (one hour to seven days, at least six hours inside the correction window), respecting longer upstream retry hints. Not-published attendance stays distinct from zero.

Snapshot payloads are gzip BLOBs keyed by reader kind, version and exact sitting ID. SQLite retains them on disk, with no term-wide payload cache in memory. Idle ticks seek metadata indexes without decoding payloads or taking a lease. `SITTING_SNAPSHOT_MAX_DISK_MIB` caps compressed snapshots and staged pages at 256 MiB by default (range 16–2048), within the activity index's overall disk cap. Bounded staged source pages let collection resume across small run budgets. Final snapshot admission counts the staged bytes it replaces; snapshot replacement and staging removal commit atomically. Reader-version changes discard obsolete projections and rediscover sittings without reopening failed calendar backoffs. One dispatch precedes core work and another follows every eight core tasks; when core work is idle, snapshots drain under the existing run budget and deadline without extra pacing.

Fresh complete snapshots require no upstream reads, including week resolution when the corresponding calendar is retained. Missing, stale or partial observations use the existing on-demand reader and submit bounded, member-independent high-priority ID hints to the sole writer. Before reusing a saved vote day, the reader compares its declared result children with the incoming calendar or meeting node. Changed declarations use the on-demand completeness checks and reopen successful snapshots for high-priority collection. Other hints preserve correction intervals, and all hints preserve failure backoff; ordinary discovery recovers lost hints after restart. Foreground readers never write SQLite. The fallback still pages at 50 rows (250 for decisions), bounds each period to five sittings and 24 MiB of sources, and has an independent 50-second loader against the 30-second HTTP budget. Local timeout/busy/cancellation errors never become parliamentary gaps. Existing response versions, snapshot identities, coverage, source hashes and retrieval dates are preserved for the same inputs.

## Member attendance API

`GET /api/member-attendance/{personId}?sittings=MTG-PL-YYYY-MM-DD,…&lang=en` (response version 1) reads one to five unique held current-term sitting identifiers, sorted canonically. Unknown, repeated and invalid query parameters return 400. The client starts this independent 35-second read only after a valid votes response settles, using `coverage.scannedSittingIds`. Errors leave votes, filters and pagination unchanged. HTTP responses use `no-store` because registers can be revised.

The reader first consults the same writer-owned per-sitting snapshot store. Snapshots retain the member-independent participant extraction, exact source evidence and all published register-language metadata. Requested-language/English selection and member projection happen on read. Missing or stale snapshots use sequential exact `/meetings/{sittingId}` reads through the existing interactive ODP cache (15-minute source TTL, 1 MiB per source) and enqueue writer hints. The fallback extraction cache stays bounded to 32 entries/2 MiB, keyed by sitting and content hash; changed content replaces the extraction. Reader cancellation ends only that reader's wait on the independently bounded 50-second shared load. Optional exact ATT metadata retains its declared PDF link and issue date; metadata failure removes only that enrichment. No attendance distribution download is added. The interface and API contract are unchanged.

`observed`, `partial`, `not-published` and `unavailable` distinguish valid non-empty participant lists, malformed references, an exact sitting without a participant field or register link, and missing/contradictory observations. Partial lists retain valid IDs internally but expose no member conclusion. Empty participant arrays remain unavailable. Same-list duplicates are counted and deduplicated; cross-list conflicts remain explicit. Counts distinguish an omitted excused list from an observed empty one. `memberStatus` is listed-present, listed-excused, conflicting or not-listed only for an observed register; otherwise it is null. Mandate eligibility remains not-assessed. Types live in `src/MemberAttendanceTypes.ts`.

## Document context API

`GET /api/document-context/{id}` lazily reads one exact term-10 A report, B motion, RC joint motion or TA adopted text. Parameters are `lang` (default `en`), optional exact `amendment` and its `list` variant, or `adopted=1`. Optional `wording-lang` requires both `amendment` and `list`; it accepts an exact lowercase two-letter source language or `unknown` for a null source language. It is independent of the body language requested by `lang`. `body=0` with an amendment reads only its wording; full document retrieval waits until context is opened. Unknown, repeated and incompatible parameters return 400. `src/DocumentContextTypes.ts` exports the response. This endpoint does not start an indexer; the motion amendment list remains index-only.

The default response contains the published body, language, notes and source metadata. An amendment first uses the checked exact index lookup. If wording is missing, the reader can parse at most four explicitly linked published DOCX lists whose identifiers include that number; ranges select candidates, never establish that an amendment exists. The resulting names are published names, without inferred member identities. Missing or conflicting wording stays unavailable. A pinned list restricts source versions to that list; `wording-lang` additionally restricts target matching to its exact source language, retaining known alternatives in the response. Only one candidate with available wording can resolve; an unreadable competing candidate still withholds the target. Published-list fallback reads only the selected language and retains other declared files as unread alternatives. The selector is echoed as `requestedWordingLanguage` only when supplied; chosen target evidence records `wordingLanguage`. Without it, existing version selection is unchanged. A different actual body language, or an unknown selected wording language, withholds highlighting without choosing other wording.

Passage matching uses unique original quotations or explicit published provision references. Quotes may span only consecutive, complete paragraphs within one source container and segment. A different quotation does not block a uniquely labelled provision, and the response records that difference. Insertions require an explicit before/after reference. Legacy extracts and unresolved objects do not establish matching boundaries. The document remains readable when a passage cannot be located.

`adopted=1` returns choices without downloading bodies: at most four exact linked procedures and eight TA candidates, each checked for reciprocal `adopts`. Missing/null source relationships and failed reads remain gaps; an adopted-text relationship does not change the original motion's outcome. Source metadata has a combined 16 MiB bound. Shared loads last at most 50 seconds, independently of the 30-second HTTP reader deadline. Local timeout, busy and cancellation failures remain retryable errors. Computed responses use a bounded 12 MiB memory cache for at most one minute; stale or retained indexed evidence gets no new computed lifetime. A separate 8 MiB/four-entry cache shares exact list extractions for up to five minutes across amendment reads, preserving the original retrieval time and content hash. API-declared file size/issue time stay separate from retrieved byte size/hash. HTTP responses use `no-store`, with query-specific ETags and conditional GET/HEAD support.

## Motion amendment API

`GET /api/motion-amendments/{id}` (response schema 2) reads the accepted index for one exact term-10 `B-10-YYYY-NNNN` or `RC-10-YYYY-NNNN` identifier, allowing four to six final digits (`server/motion-amendments.mjs`, `src/MotionAmendmentsTypes.ts`). It never fetches upstream sources, queues work or writes data. The hidden amendment catalogue remains hidden.

Query parameters are `member` (positive Open Data person ID), `scope=all|member` (default `all`), `lang` (default `en`), `offset` (default `0`, maximum `1000000`), `limit` (default `20`, maximum `50`) and optional `amendment` (an exact individual amendment ID belonging to the queried text). Member scope requires a valid member. Unsupported, invalid or repeated parameters return HTTP 400. All scope with a member annotates each checked aggregate and variant match without filtering out other proposers; member scope uses the same checked, dated author matching. `total` counts the selected indexed scope; `totals` also gives all indexed rows and member matches.

`selection` retrieves the requested amendment independently of the current page and member filter. It reports the requested identity, checked item, availability, membership in the requested scope and presence on the page, without changing `items` or totals. `amendmentById` applies the same read protections as a page and accepts only the primary indexed identity or an exact published `officialIds` alias within the target and serving generation. Missing or ambiguous identities produce an unavailable selection; no other record is substituted.

The response keeps queried-text authorship, amendment proposers and exact original/joint relationships independent. Each motion text includes its indexed whole-motion `outcome`; this is independent of amendment outcomes and selected-member position. Motion result sources do not contain the selected member's named ballot, so `memberPosition` remains unavailable. Contradictory indexed decision bindings withhold the outcome; conflicting counts withhold totals while preserving an unambiguous announced outcome. `outcome.totalsStatus` and `evidenceGaps` describe that distinction.

Related texts are capped at five per direction and are not a complete relationship census. `relations.adoptedTexts` requires an independently indexed exact `TEXT_ADOPTED` record with an explicit `adopts` reference to this motion. It transfers no authorship and does not establish that the original motion was adopted separately. Current source projections do not generally collect these adopted records; `adoptedCoverage` reports unavailable evidence rather than inventing a relation. Body retrieval and bounded discovery remain separate capabilities; this endpoint neither fetches text nor substitutes an adopted body for its original.

Each amendment retains list and individual identity, provision, proposer and on-behalf-of evidence, conflicting variants, actual wording language and field-level provenance. `wording` distinguishes available, withheld and unavailable columns. Each decision has whole-amendment, split-part or unresolved-split scope; `wholeAmendmentOutcome` excludes split-part decisions. Split descriptions do not establish validated wording spans or survival in adopted text. Original/joint/adopted comparison remains a separate API.

`coverage.resultState` distinguishes records, not indexed, no indexed member matches, observed empty and unavailable evidence. The existing writer records `emptyObservation` only when the current document projection explicitly publishes an empty `inverse_foresees_change_of` array. With no retained amendment rows, that establishes `observed-empty` for `observationScope=published-amendment-list-relationships`; it establishes neither absence of oral amendments nor complete decision coverage. Missing, unknown or legacy relationships cannot establish emptiness. `observationComplete` is limited to the stated source scope, while legacy `complete` remains false for this narrow empty observation. `backgroundPending` has global index scope, and `targetProcessing` stays unknown. Keep retained/stale evidence and gaps visible, including on later pages; `snapshots` identifies the amendment and text generations separately.

`MotionAmendments` is the controlled inline reader for a selected MEP and exact B/RC text. The parent owns original/joint text choice, URL/history and scroll restoration; use separate state per exact text or clear amendment/list/page selection when changing it. The reader loads fresh 20-row member-first pages on demand, retaining accepted pages by full query across closing and navigation. List and exact reads publish in request order, with cancellation and retry; working-generation equality does not prove unchanged content. Off-page and alias selections require successful current exact validation before wording or context is shown. An alias match within one page does not establish uniqueness. Older snapshots cannot replace accepted data, and highlights use checked per-variant matches. The catalogue remains hidden.

The reader's `renderContext({documentId, amendmentId?, listId?, wordingLanguage?, view, onBack})` callback delegates source-body rendering to the parent. Amendment context pins its checked source-list language, including explicit unknown language; body-language selection remains separate. `contextTarget='text'` opens the exact chosen motion independently of amendment availability, including an invalid linked amendment; `contextTarget='amendment'` requires a checked amendment and exact wording-list ID. `view='adopted'` passes the same B/RC target to the verified adopted-text resolver. It never substitutes adopted wording for the original or claims that an amendment survived. The reader focuses context on entry unless the parent has focused a target inside it. Back retains reader state and restores focus without scrolling.

Political activities mounts this reader lazily for B/RC documents. Its parent keeps the activity page, exact original/joint text choice, amendment/list/language, adopted-text choice and numeric scroll positions across tab changes and browser history. Changing text clears amendment selection. Duplicate reader query fields remain invalid after App canonicalization. Scroll restoration waits for the selected activity and source body to finish loading; a loading shell cannot replace the saved reading position.

## Following

Following keeps local state in `ep.following.v2`. Each MEP has nondecreasing activity/answer marks within an epoch. Entries retain exact IDs, categories, source languages, first-discovery timestamps and optional read timestamps. New state lasts until an entry is opened or 24 hours after discovery. The browser retains up to 200 new entries plus the five most recent read or expired entries, with explicit omission counts and profile links. Up to ten new entries expand inline through the profile’s exact source-ID lookup and readers; larger sets show a type summary. Opening an entry acknowledges only that kind and ID. Opening Profile and leaving Following acknowledge nothing. Mark all read advances seen marks and clears signals. A shared expiry timer updates the navigation badge without a storage write. Metadata corrections do not flag MEP activity; questions retain revision/answer baselines. An epoch change re-baselines markers, keeps entries, and displays a restart note. New follows baseline the archive. The validity guard accepts 1,000 MEPs; questions remain limited to 100.

Checks run on load and when the follow selection, language or Following view changes, on every page. While visible, the browser retries unprepared snapshots or failed checks after one minute, then waits four hours after successful preparation. Focus and visibility changes resume checks when due. Hidden tabs make no automatic checks. Status reads are throttled to once per minute, with explicit checks bypassing the throttle. The navigation badge counts followed items with new updates, never the total number followed; multiple updates for one item count once. Manifest processing, question POSTs and pending migrations complete separately for the epoch, generation, readiness, language and item save identity. Question checks run independently of MEP marker readiness and manifest failures, with separate check states. Failed tasks retry on focus or explicit Retry without waiting for another generation. Unready markers and failures retain readable updates and show uncertainty. Migration carries unread and compares complete v3 baselines through one detail request per legacy MEP; incomplete baselines start from the manifest without flagging the archive. The minimal `ep.bookmarks.v1` mirror contains the earliest 100 follows of each kind; `legacyKeys` tracks exactly this set, so old-tab removals cannot discard follows beyond the mirror. Failed follow writes revert with an alert; failed background writes retain in-memory changes and show a persistent retry banner. Browsers without storage keep follows for the tab only.

The client uses the marker protocol. `GET insights/following-status` returns `{epoch, generation, marksReady, indexComplete, publishedAt}` with a 60-second public lifetime. `GET insights/following-manifest?epoch=…&generation=…` returns the frozen roster map of `[activityMark, answerMark, activityCount, answerCount]`; null marks with zero counts mean no indexed items. `GET insights/following-member?member=…&epoch=…&generation=…&lang=…` returns all current identities as `[sourceId, kind, mark]` (`kind`: 0 activity, 1 answer), plus at most 200 rich `entries` ordered by mark, date and ID descending. Each entry adds string `kind`, `mark` and the indexed `category` to the saved preview fields; `truncated` counts identities without rich previews. Missing members return `outside-roster` and empty lists. Both responses include `rosterBasis`: `publication` for a frozen publication roster, or `preparation` for a backfilled snapshot whose historical roster is unknown; interpret absence only against that basis. No `since` or reading state is accepted. Manifest and detail support the serving and retained previous generation, with one-hour browser/CDN lifetimes and ETags; other epoch/generation pairs return 409 `generation_changed` with the current epoch/generation in `error`. Until a published summary exists they return 503 `marks_unavailable`. Include the normal `v` API parameter for CDN caching; unversioned reads remain CDN no-store.

`item_marks` retains the first published generation for each exact `(mep, kind, source_id)`, including vanished identities, independently of source dates. Publication assigns marks for touched source keys and updates affected summaries from distinct-identity additions/removals, copying unaffected roster rows. Removing a maximum mark or adding a roster member rebuilds that member’s aggregate; missing prior summaries require a full build. Marks use integer kinds in a `WITHOUT ROWID` table. Marks and summaries commit atomically; working generations never assign marks. Summaries and publication timestamps follow the items generation lifecycle. A recreated database has a new random `marksEpoch`. Offline preparation uses the independent `followMarksVersion`, marks previous before active, excludes unfinished work, and records the active `markBaseline`; it does not rebuild `activityReadVersion`. A pre-existing previous publication timestamp is unknown and remains null. Summaries backfilled for retained generations use the roster available at preparation, since historical rosters were not retained. An empty roster leaves marks unready until a subsequent publication with a roster.

`POST insights/saved?lang=…` accepts only `{questions:[…]}`: up to 100 distinct valid question IDs in an 8 KiB JSON body. It returns saved-question states with no-store caching, under the same API version handling as corpus POST. GET supports questions only; MEP selections are rejected. The API version bump makes stale tabs reload before using the removed contract.

While Following is visible, changed MEP marks automatically resolve through detail reads, with at most four concurrent requests and one resolution per epoch, generation, language and follow identity. Failed detail reads retry on focus/visibility after 60 seconds, or through Retry. First-signalled timestamps start the 24-hour window even if resolution is delayed. Question revision-only changes expire after 24 hours or clear when the question is opened from Following. Unavailable observations and incomplete index coverage remain explicit; marker checks read the existing index and do not establish complete publication coverage.

## Error diagnostics

The browser reports failed same-origin API fetches (including gateway HTTP errors), network failures, errors rendered through `uiErrorText`, and React boundary/unhandled errors to `POST /api/client-errors`. It excludes normal `AbortError` cancellation. Reports are best effort: failures while offline or while the reporting route is unavailable cannot reach the log. HTTP fetch events include prefetches and retries, so counts describe observations, not distinct affected readers. Existing data-gap labels in successful responses are not error events.

The API records caught request failures with a generated `X-Request-Id`, status, stable error code, public error message, source locations, elapsed time and `APP_REVISION`. Browser HTTP events carry the response request ID when present; browser records are untrusted reports. Free-form browser error text, page URLs, search text, request bodies, saved/followed items, cookies, IP addresses and user agents are excluded. Only request paths and bounded public selectors (language, version, date, document/member identifiers and pagination) are retained. UI failures use stable message IDs, error types and up to three source asset locations (file, line and column); arbitrary browser messages are omitted.

Logs are private JSONL files in `ERROR_LOG_DIR` (default `var/diagnostics`; the runtime image sets `/data/diagnostics`). Mount that directory on persistent storage outside the served tree. One process must own each directory. Rotation keeps the current 5 MiB file and three previous files (about 20 MiB total); the write queue is capped at 256 events. Disk failures emit a fixed stderr warning and never fail a user request. There is no public log-reading route. Browser reports are capped at 30/minute per page and 120/minute per server process, with a 4 KiB body limit and the existing same-origin validation. Deploy gateway admission for POST on the reporting route alongside the application; keep it uncached.

For batch triage, run `node scripts/error-summary.mjs /path/to/diagnostics` on the host. It emits JSON grouped by source, kind, request path, status and error code, with counts and first/last observations. Server and browser observations remain separate. Read the JSONL request IDs for detailed correlation. Rotation bounds retained history by size rather than time.
