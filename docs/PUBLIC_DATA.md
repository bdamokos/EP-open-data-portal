# Public data sources

This page lists the external sources the application uses, what each provides, and the quirks a contributor needs to know. It describes current behaviour. Change history belongs in Git and pull requests.

| Source | Use | Access |
| --- | --- | --- |

## Access rules

- Every source is anonymous. No adapter uses credentials, private exports or copied production caches. A failed public request becomes a reported gap. It must never lead to credentials or to bypassing a protection such as DOCEO's browser verification challenge.
- Server routes are read-only. Callers cannot choose an upstream host, supply upstream query text (such as SPARQL) or make the server follow a URL. Corpus search runs user queries only against locally stored text. Endpoints are built from validated identifiers (`server/odp.mjs`, `server/source-record.mjs`, `server/legal-references.mjs`).
- Requests never forward the caller's cookies or authorization and never forge an Origin. Open Data API and portrait downloads reject redirects. OEIL and Publications Office reads follow same-origin redirects only (`server/official-context.mjs`). Downloads stream within size limits.
- The [Open Data API v2 specification](https://data.europarl.europa.eu/api/v2) publishes a maximum of 500 requests in five minutes to the same endpoint. Because endpoint scope is not defined more precisely, the application conservatively shares one rolling 500-start allowance across all API v2 endpoints, IDs, languages and query strings. Foreground reads, Atom feeds, index/corpus metadata and retries use the same allowance; coalesced readers and cache hits add no requests. The exact five-minute boundary remains counted. Background jobs leave 50 starts available to foreground readers as a local fairness rule.
- The API quota does not cover website portraits, RSS, document distributions, Multimedia Centre/player metadata, OEIL or Publications Office SPARQL. Their public references below document no equivalent numeric allowance; local concurrency and size bounds are resource safeguards, not claims about source terms. RSS, distributions, Multimedia Centre/player metadata and each official-context origin use separate admission pools (two active operations, at most one background-owned admission at a time). Portraits retain their separate bounded image pool. Source-specific 429/503 pauses honor valid `Retry-After` seconds or dates without shortening them; missing or malformed hints use a 60-second fallback (`server/upstream-queue.mjs`). No mandatory two-second delay applies to API requests.
- Use one source-cache writer, one leased activity-index writer and, when enabled, one leased corpus writer that opens the index read-only. Page views never start an indexer or a corpus download.
- Join records only by exact identifiers, never by title, tally or name similarity. Keep source URLs, retrieval times and languages. Missing observations stay null or explicit gaps, not zeroes.
- Question and document titles decode one layer of named and numeric character references as plain text. Raw source records, language keys, identifiers and provenance remain unchanged; decoded markup is displayed as escaped text. Activity previews decode retained title literals when read, without rebuilding the index.
- Caches, indexes, corpora, recording catalogues, following data and hosting configuration stay outside Git.

`server/public-data-policy.test.mjs` and `server/public-serving.test.mjs` enforce the routing and configuration boundary.

To add a source, document it here (access path, licence, limits), route it through the existing client, cache and queue, and add a small test fixture that records its source URL and retrieval time.

### Character references

The handwritten text decoders share `server/character-references.mjs`. Each adapter selects its existing policy; all require semicolons and decode one layer per call. Decoded markup remains text and still needs output escaping. Raw records, identifiers, language keys and provenance are unchanged.

| Adapter | Named references | Numeric references and invalid input |
| --- | --- | --- |
| `source-titles.mjs` | Case-sensitive `@nodable/entities` `ALL_ENTITIES` table | Decimal and `x`/`X` hexadecimal; preserve zero, surrogates and values above U+10FFFF. Non-string values pass through. |
| `member-votes-model.mjs` reference text | Five XML names, case-sensitive | Decimal and lowercase `x` hexadecimal; preserve zero, surrogates, values above U+10FFFF, C0 controls except tab/LF/CR, and U+FFFE/U+FFFF. |
| `press-releases-model.mjs` `decodeHtml` | Case-insensitive XML names plus `nbsp`, curly quotes, dashes and ellipsis; `nbsp` becomes an ordinary space | At most seven decimal or six hexadecimal digits (`x`/`X`); preserve zero and values above U+10FFFF. Existing surrogate/control decoding and string coercion are retained. |
| `amendment-splits.mjs` descriptions | Five XML names, case-sensitive | Decimal and `x`/`X` hexadecimal; unsupported references produce `unsafe_xml`, invalid numeric values or C0 controls except tab/LF/CR produce `invalid_xml`. Existing U+FFFE/U+FFFF decoding is retained. |

Unknown or malformed references stay literal except in split descriptions, whose XML checks reject them. Split descriptions unwrap a fully escaped `partValue` fragment at its boundary, then decode text nodes once; CDATA stays literal. XML validation still applies before text decoding, including rejection of uppercase `#X` in an ordinary fragment. Press feeds retain their XML-parser layer followed by their title-text layer. Tag removal and whitespace handling remain in the adapters.

Other XML readers use `fast-xml-parser`; OEIL enables its HTML entity mode. `src/Transcript.tsx` uses the browser's XML `DOMParser`. Those parsers own tree, attribute and CDATA handling and do not add a second shared-helper pass. There is no handwritten character-reference decoder in `src`; its following-store `decode` functions read JSON.

## Source notes

### Current member directory

Member lists sort by the displayed full surname (including particles such as “del”), then given name, using fixed English collation with accents significant and case ignored. Numeric member ID breaks ties. The EP `sortLabel` is retained as source metadata but is not an ordering key: it can concatenate surname and first initial without a separator. The Members wall, its country/group/committee filters and the amendment author picker share this ordering; Following keeps its saved-item order.

The directory exposes the current roster and exact committee catalogue identifiers before optional detail reads finish. Retained multilingual names and source freshness remain available; missing names fall back to exact committee codes. Committee filters show known members with explicit incomplete coverage until all current profiles are available. Membership retries read missing profile IDs only.

Profile `countryCode` and `groupCode` come from `/meps/show-current`, joined only by exact `identifier`. The per-MEP record supplies country authority URIs on mandate memberships and political-group organization IDs, rather than these roster codes; citizenship is not country of representation. `currentAffiliation` records the Brussels observation day, person ID, match status, roster source URLs, retrieval dates and stale markers. It describes the current roster, never historical membership. Missing codes, non-current members and unavailable or ambiguous roster matches return `null`, with match status and errors distinguishing these cases. Roster failure preserves the rest of the profile and is uncacheable at the response layer.

The `hasEmail` flag describes a non-empty email in the source record: omitted contact data is `null` (unknown), an explicit empty value is `false`, and a supplied email is `true`. The directory initially has roster evidence only; once an exact-ID profile is loaded, its email flag enriches the directory too. Thus a partially loaded directory can report unknown while a profile reports true. `hasCv`, `hasNews` and `hasVideo` are `null`: these capabilities are not established by this adapter. None of these flags infer absence from an omitted property.

Current-member profiles show role periods for their active committees. Profiles without a current-roster match retain readable open committee records under “Committee records”, with omitted end dates explicit and no current-role claim. The MEP API supplies each role and its dates; corporate-body `isVersionOf` relationships connect temporal versions of the same committee, including midterm reconstitutions. Matching names or abbreviations never establish continuity. Consecutive, non-overlapping periods of the same role and classification are combined for display; role changes, gaps, unknown dates and conflicting roles remain separate. Original membership IDs, body IDs, periods and source retrieval dates remain in the profile response. Older periods can span legislative terms; their dates describe service in that committee, not a new appointment inferred from a midterm boundary.

Profile-only enrichment shares one eight-second optional deadline across affiliation/role labels and committee history, using the existing source cache and queue with at most two reads at once. Political affiliations take priority, then valid start dates from newest to oldest, including open periods, with at most 16 additional exact corporate-body reads; committee history retains its 64-body bound. Missing, stale or mismatched labels preserve readable identifiers and successful profile fields, with retry through the profile reader. Retrying refreshes rejected member observations, body identities, classifications or missing labels while reusing valid cached records; a failed refresh preserves readable data. Directory and feed indexing do not perform these body lookups.

Two collapsed sections show political affiliations, delegations and other roles, including governing and working bodies and Parliament-level offices held as President, Vice-President or Quaestor. They retain individual membership, body, role, classification and date observations, including language maps, body relationships, source URLs, retrieval dates and freshness. Labels require an exact body identity and classification match; equal names and `isVersionOf` never combine these records. Missing membership observations differ from a verified empty list. Malformed or incomplete observations remain in the raw data with explicit coverage issues; supported rows remain readable. Label completeness is separate from observation coverage and date issues. Missing or invalid dates are shown explicitly; an omitted end date never means “Present”. Dated national-party and political-group records do not establish current affiliation. Records with valid bounded periods sort latest first, followed by uncertain periods.

The profile’s “MEP since” date requires an exact current-roster match and comes from explicit `MEMBER_PARLIAMENT` memberships of `org/ep-N` bodies in the same MEP record. Consecutive mandate periods combine into continuous service across parliamentary terms. A gap starts a new spell; earlier service is displayed separately. Profiles outside the current roster remain accessible and show retained periods under “Parliamentary service”, including explicit missing end dates; roster absence never supplies a departure date. Committee roles, party memberships and the current term’s opening date never substitute for missing mandate dates. The response retains the source mandate IDs and dates; ambiguous or invalid observations remain explicit gaps.

### Reading a document in context

The lazy context reader uses the exact `/plenary-documents`, `/procedures` and `/adopted-texts` records and their declared DOCX files. It can read one amendment from at most four explicitly linked published lists when indexed wording is missing; list-number ranges select candidates, while the actual parsed individual number establishes inclusion. An explicit `wording-lang` pins the source language within an exact amendment and list, independently of requested body language. `unknown` selects a null source language; it cannot establish the body's language. Known source alternatives and provenance remain visible; conflicting or unreadable same-language candidates withhold matching, and body-language fallback never selects different amendment wording. This read does not alter the index or resolve published proposer names into member identities. Adopted-text choices require an exact procedure link and reciprocal `adopts`, independently of the original text's recorded outcome.

Source paragraphs retain their XML locations, boundaries and unsupported objects. A quotation match cannot cross an omitted block or table cell. The compatibility target can identify a published reference even when its quoted wording differs. Amendment overlays use a separate conservative placement: original/proposed columns establish insertion, replacement or deletion; complete resolution units establish source extents, and replacement/deletion wording must agree with the complete unit after whitespace and leading-number normalization. Suffixed insertions follow the preceding sibling and its points, dash lists and continuations. Only complete consecutive body rows retain parent scope; tables, source gaps and incomplete rows break it. Annex headings (including numbered and titled forms, with titles after Word soft breaks) and explanatory-statement/justification headings in all 24 supported languages cap resolution extents; English signature and notes headings also end the body. Heading-like unclassified rows, including title-case colon headings, close lists and withhold the preceding provision as `resolution_extent_uncertain`; later numbering does not establish its extent. Quote fallback searches only inside the resolution and requires a complete, certain provision. An insertion after the final unit stays unresolved when no explicit end is available. Conflicting evidence, duplicate labels, incomplete passages or different wording languages withhold placement. The proposed diff then appears above the unchanged document. Replaced spans preserve source links and note markers on unchanged and deleted original wording in both diff modes when the source and amendment original match after whitespace normalization. Otherwise a short notice directs readers to the original document; the notes list remains available. Overlays cover B/RC resolutions and the resolution inside A reports. An unknown comparison heading may use only an exact motion/report identity and a verified resolution body; it cannot select a Commission proposal. Commission proposals and other legislative baselines are unavailable until their own source text is supported. Proposed changes do not establish adoption. The original, joint and adopted text stay separate documents. Missing text or relationships remain unavailable rather than proving that no amendment or adopted text exists.

### Member voting records

`GET /api/vote-periods` reads only the public `/meetings?year=` catalogue for every year from the current term’s start through Brussels today. It groups exact held sitting identifiers into Monday weeks and reports per-year paging, budget, error and source-freshness evidence. This calendar coverage is separate from the selected period’s voting-record coverage. Sitting days without decisions remain in the calendar. For an exactly verified held sitting, a first-page HTTP 404 from a decision, result or agenda collection is retained as an empty-collection observation with its URL, retrieval date, HTTP status and response-body hash. A 404 for the current Brussels day remains partial because that sitting may still be in progress; this is not a publication SLA. Declared-child checks still prevent contradictory gaps from being labelled complete; other failures remain unavailable. Only complete sitting observations with zero decisions receive the no-votes marker.

The member voting API reads a selected held plenary week or sitting through `/meetings`, sitting `/decisions`, `/vote-results` and `/foreseen-activities`. Named roll calls use `vote-method=ROLL_CALL_EV` without `filter-output=voters`; a separate voter-excluded decision read retains non-named and lapsed outcomes. Exact decision parents, result children and agenda references connect documents, procedures, amendments and split components. Procedural ballots without agenda links remain available with unresolved context. English reference labels provide an explicitly labelled scope heuristic when no exact amendment/component reference exists. Subject groups use exact vote-result identities and keep whole-text source decisions separate from individual amendment/part outcomes. Ambiguous forward/inverse parents and conflicting source projections withhold enrichment. Decision `referenceText` values decode one layer of standard XML named/numeric character references for display; plain activity labels, percentages, unknown references and retained source payloads remain unchanged.

Document text and display titles prefer the requested language, then English, French, Spanish, German and remaining languages alphabetically by ISO code. The original language retains its label but has no display priority. Readers offer the available languages using their self-names and identify any fallback. This display order does not select amendment ingestion sources, wording evidence or placement languages. Vote subject titles use the same monolingual order before `mul`. The display parser (`src/voteTitles.mjs`) can extract English/German segments from the complete French–English–German agenda-title format in `mul`, requiring the supplied French label as an exact whitespace-normalized anchor and matching weekday headings. Explicit language fields take precedence. The original language map stays unchanged, and the full source literal remains in the title tooltip. Unrecognized or ambiguous formats remain unsplit; French-only decision labels do not acquire translations from their parent subject.

Bounded result pages also retain public roll-call, split and separate-vote request nodes. Exact decision component references can expose supplied split XML literals and decoded wording with sibling descriptions and source URL/hash/JSON-pointer provenance. A roll-call requester is attached only through the decision's exact `was_motivated_by` request edge and its unique result parent; similar labels and narrative request scopes are insufficient. Missing requester evidence remains unavailable. Document bodies are not fetched for this collection.

Actual `had_voter_favor`, `had_voter_against` and `had_voter_abstention` positions stay separate from `had_voter_intended_*` declarations. Non-named votes and missing positions never establish individual choices or physical absence. Omitted declarations are not reported as proof that none exist. A roll-call method on a lapsed decision does not establish a conducted ballot. Null tallies remain distinct from zero, and conflicting/malformed named references and tally mismatches remain explicit. Current roster metadata is not used as historical group membership or mandate eligibility. Outcome alignment compares conducted, recorded For/Against/abstention positions with the official ADOPTED/REJECTED result, never tallies or intentions. Other observations stay unclassified. The member-votes alignment filter applies before pagination to the pinned period snapshot; counts cover all observed decisions before either filter and are unavailable when vote coverage is unavailable.

Source coverage is bounded and independent of the activity index. Complete collection requires successful paging and all declared result/decision children; source errors, repeated pages and caps retain uncertainty. Retrieval times, content hashes and stale/refresh flags identify the source snapshot; no API publication SLA or publication version is inferred. Parliament's [roll-call annex](https://www.europarl.europa.eu/doceo/document/PV-10-2026-10-07-RCV_EN.xml) states that corrections/intention declarations do not change announced results and may update over the two weeks following a part-session. The endpoint is a selected-period observation, not a complete term history or participation statistic.

Question Subject chips identify place names in English titles using the retained country-label catalogue and explicit aliases (for example, US and United States). Clicking a chip filters by that place identifier within the selected analysis period, combined with addressee, election-country and date filters. Choosing a subject clears the generated topic/word selection and pagination. These are derived title annotations, not official subject indexing; titles without a recognised place are excluded from a subject selection. Text search has its own scope across all topics and subjects.

### Open Data API

Sitting calendars share `server/meetings-reader.mjs`: one bounded, coalesced `/meetings?year=` observation per current-term year, with page URLs, retrieval times, content hashes, freshness and coverage. Complete fresh observations are reused in memory for one minute; source pages use the existing 15-minute ODP cache. Each year has independent page, row and byte limits. HTTP 204 ends paging only after a successful page. Repeated pages, conflicting identities and mismatched year/date/URI records leave explicit gaps. Current-term future sittings remain available to agenda readers; Votes uses held sittings through Brussels today.

| Reader | Meeting data and navigation |
| --- | --- |
| Vote periods and Member Votes | Shared yearly catalogue; Monday weeks and held sitting days. Exact selected sittings retain a separate full `/meetings/{id}` identity check. |
| Legislation, What’s hot and Word cloud | Shared yearly catalogue, including future sittings; the common period picker offers weeks and individual days. Nested reads use the same catalogue observation. |
| Live plenary | Today’s `/meetings/{id}/foreseen-activities`; no catalogue scan or sitting picker. |
| Activity index and amendment outcomes | Exact sitting decisions and results discovered from document relationships; no catalogue scan. Legacy stored vote-week hints read the index only. |
| Source-record inspector | A bounded view of the requested public meeting record or collection; no calendar assembly. |

Incomplete calendars keep known sittings selectable and carry the same per-year coverage into agenda, participation and cloud responses. Missing selections remain unavailable while coverage is incomplete. The default latest week is unavailable if a missing year could contain a newer sitting. The response keeps known calendar options with no selected sitting; explicit known periods and saved links remain usable. These responses use `no-store`; partial or refreshing browser observations recheck on reopening. Assembled views retry after one minute, and cloud recovery restarts pagination. An HTTP 204 agenda stays unavailable and its sitting stays selectable. Full exact meeting records remain separate from catalogue observations, so attendance readers can retain participant fields and independent validation.

- `/meetings` accepts comma-separated years and offset pagination.
- Speech and date-range filters have no span limit in the API. The current term starts 16 July 2024.
- Records can contain fields such as `notation_codictPersonId`. These are fields of the open API, not calls to another service.
- `/meps/show-current?mandate-date=YYYY-MM-DD` gives the dated roster. Use it, not today's roster, to classify historical speakers.
- The [API v2 specification](https://data.europarl.europa.eu/api/v2) documents `/plenary-documents/feed`, `/committee-documents/feed` and `/parliamentary-questions/feed` as fixed last-month Atom feeds, without date-range parameters. `/procedures/feed` supports `timeframe=custom&start-date=YYYY-MM-DD`; it documents no `end-date`. These four feeds document neither pagination parameters nor an entry limit. An advertised next page is treated as incomplete coverage, not silently ignored.
- Activity cycles filter feed updates from the previous successful run minus two days. Procedure feeds receive that start date; document/question feeds are filtered locally. Initial discovery and gaps longer than 28 days page selected catalogues for new IDs only, retaining all previously stored records. A gap outside the fixed monthly feed remains explicit; bounded mutable-record checks do not establish complete historical update coverage. Speech catalogues cover the interval since the previous success minus two days; they do not restart a full-term refresh after a missed day or every Sunday.
- An indexed queue rechecks at most 100 mutable documents per daily cycle, no sooner than seven days after retrieval or the previous scheduling attempt. Eligibility uses distinct official languages in the existing file projection and exact `inverse_answers_to` answers: unanswered written/oral questions and documents or embedded answers with fewer than 24 language versions remain eligible. Unobserved language/answer relationships stay unknown. Answered questions with all 24 question and answer languages, and other documents with all 24 languages, are final.
- Core source failures stop blocking publication after three attempts for HTTP 404/410 or five for other failures. Their exact identifiers, pagination state, error and retrieval context remain durable coverage gaps, with at most 25 slow gap retries per daily cycle after seven days; sitting failures inside the correction window retain the six-hour cadence. A first usable current roster is required. Publishing an incomplete observation enables incremental scheduling without claiming complete coverage or exact totals. Failed feeds retain their original interval across partial publications; expired monthly intervals discover new IDs through that collection’s catalogues even while the feed is unavailable or awaiting retry, and retain an explicit historical window gap. Ordinary discovery cannot reopen recorded failures or replace their saved cursors; only bounded retry admission may do so. An admitted retry keeps its progressed cursor across queues, checkpoints and generations and cannot be admitted again until it completes or records a new failure. Each newly expired feed interval has separate durable catalogue discovery, independently of persistent coverage labels. Gap records disappear only after their saved task completes successfully; unresolved monthly-window gaps remain visible. A runtime rollback that advances the active generation without its accepted refresh snapshot stops serving complete coverage and refuses further writes until matching state is restored or reconciled offline.
- Following markers describe first appearance in a published local index generation, not Parliament's publication date. Distinct activity/answer identities are tracked per exact MEP ID, with answers attached to each question author; categories do not multiply counts. Metadata-only changes do not advance a marker. A frozen roster manifest includes zero counts for members without items, and preserves incomplete coverage separately from zero. Initial unfinished loads or an unknown roster cannot supply markers. Removed identities retain their marks if they reappear; rebuilding the database changes its epoch. Routine status/manifest reads reveal no MEP follow selection. Member detail requests reveal interest in one MEP, including one-time legacy migration reads for followed MEPs with complete baselines; they send no reading state. Question POST keeps selected IDs out of URLs but still sends that selection to the server. Following and reading state remain in the browser. Status checks on load/focus are throttled to one per minute. While Following is visible, it automatically fetches following-member for followed MEPs whose manifest marks exceed the browser’s seen marks, with at most four detail reads at once. This reveals which followed MEPs currently have news, like opening their pages. A new follow establishes a baseline without presenting the archive as new. Entries survive index rebuilds. New labels last until the entry is opened or 24 hours after first discovery; leaving Following acknowledges nothing. Up to ten new entries are expandable inline; larger sets show a type summary and profile link. The browser retains up to 200 new entries and five recent read or expired entries per item, with explicit counts and profile links for omitted entries. Storage failures are shown and can be retried.
- Membership updates use the public ODP v2 [`/meps/show-outgoing`](https://data.europarl.europa.eu/api/v2/meps/show-outgoing) and [`/meps/show-incoming`](https://data.europarl.europa.eu/api/v2/meps/show-incoming) current-term lists, fully paginated. These endpoints do not declare a `parliamentary-term` parameter; the mandate filter is the term-10 guard. Only exact person and `MEMBER_PARLIAMENT` mandate identifiers in `org/ep-10` are used. Each list retains its last complete observation and retrieval URLs/times when a fetch fails, alongside the last attempt time and short error; a missing observation is unavailable, and malformed records are counted and skipped. Mandate boundaries, first-publication marks and current-roster comparisons are frozen per index generation in the public `following-membership` view. Contradictory evidence remains unverified. A former-MEP label requires an ended latest mandate and absence from that frozen roster. The browser's separate `ep.following.membership.v1` store establishes a starting generation on first availability, recovery from server-reported unavailability, epoch change and each new follow’s first successful snapshot, suppressing historical backlog. Recovery baselines are independent for each list; event list provenance lets the healthy list continue reporting updates. Client request or verification failures preserve availability and baselines, with one retryable Following-page error. Server-reported unavailability appears once on that page. Membership updates have independent acknowledgment and unbounded small history; activity acknowledgment does not clear them. Departed MEPs stay followed; their profile/activity destination explains the tracking limit and links to the official EP profile. No additional activity indexing or automatic unfollowing occurs.
- Political-group history uses term-10 `MEMBER_PARLIAMENT` mandates and `EU_POLITICAL_GROUP` periods from public ODP v2 `/meps/{id}` records. The worker reads the exact raw profile cache key while within its seven-day TTL; missing or expired records use sequential, budgeted requests, with at most 150 person refetches per index cycle. Current-MEP history can be up to seven days old unless the EP feed triggers a profile refresh, so a group switch may appear with that delay. The worker explicitly refreshes outgoing persons within the same 150-person-per-cycle budget because current-member feeds do not refresh them. Missing/oldest attempts lead later cycles. `/corporate-bodies/show-current` supplies display codes; exact `/corporate-bodies/{id}` records supply stable `isVersionOf` identities, cached daily. Names and codes never establish identity. Same-organization role periods merge across inclusive adjacent dates, clipped to mandate intervals; source membership IDs, URLs and retrieval times are retained. Mandates remain separate from group periods. Gaps, unmapped organizations, malformed periods and overlapping different groups prevent complete coverage; overlaps retain explicit ambiguous date ranges. Missing evidence never implies NI.
- Group history and its coverage progress are frozen synchronously at index publication into generation snapshots, retained/pruned with the index. Public `group-history` and `following-groups` views accept only epoch and generation, serve retained snapshots, return 409 for a changed epoch/unretained generation and 503 before a snapshot is available. Failed acquisition keeps the last good observation with stale/error provenance. Switch events require adjacent different affiliations within a continuous mandate and an effective date no later than the Brussels publication day; a mandate gap restarts service without a switch. A fresh complete person observation retracts absent switch identities; corrected dates/organizations create distinct identities with durable first-publication marks. The independent `ep.following.groups.v1` browser store establishes each followed person's baseline only on first complete history, a new follow, epoch change or recovery from observed per-person unavailability. Existing membership/activity stores and old-tab writes do not affect it. Fetch/validation failures preserve baselines. Group acknowledgments are independent; the card's Mark all read clears activity, mandate and group updates together. Dated personal affiliation uses that response generation's frozen history, indexed once by exact person ID. Question authors, agenda/document roles, participant cards, named voters and intended corrections use inclusive membership dates. Participant cards use the latest linked role/contribution date; individual roles use their own dates. Missing dates, dates outside term 10, missing history and ambiguous membership retain the existing current-group fallback without a disclaimer. Complete mandate evidence outside every mandate suppresses the group. Speech responses and speaker lines remain unchanged, including explicit speaking/committee designations; no personal affiliation is added. Profile headers, Members, contributor ordering by current full-roster group sizes, charts, filters, Group voices and on-behalf-of counts retain their existing basis. The member-votes history note is unchanged.
- Filter-coverage suggestions are computed only in the browser from the existing public directory and membership snapshot. The separate `ep.following.coverage.v1` store remembers fully followed country, group and committee sets (including singletons), last observations and dismissals. Combined filters are not tracked. Committee matching shares the Members list predicate and requires a complete membership index; missing country/group codes never establish a newcomer. Newly matching MEPs can be followed or dismissed; explicit unfollowing drops affected coverage, and nobody is unfollowed automatically. Suggestions name the coverage and use verified mandate or committee dates where available; group changes currently have no date. Coverage and dismissals are never sent to the server. Storage errors appear once on Following with a retry.

- The Questions timeline uses saved document dates before country, topic, addressee and selected-range filters. Written, priority and oral questions retain separate availability evidence. The frontier day and any crossing week are partial; later dates and failed empty intervals are unavailable, with null counts. Earlier zeroes mean no matches in the checked saved snapshot, never no parliamentary activity. Positive records remain visible through partial coverage.
- Parliamentary questions can be tabled by Members, political groups or committees ([Rule 142](https://www.europarl.europa.eu/doceo/document/lastrules/RULE-142_EN.html), [Rule 144](https://www.europarl.europa.eu/doceo/document/lastrules/RULE-144_EN.html)). The [question data model](https://europarl.github.io/eli-ep/dsd/parliamentary-questions/#participation) separates person authors from organisations and addressees. The Questions view counts exact person-author IDs as MEP authors at tabling and distinguishes current and former MEPs using the saved current roster. Its author total includes both; demographic charts cover current MEPs only. This question-specific classification does not apply to plenary speakers.
- Document-reader author identities come from exact API person creators or `AUTHOR` participations. Those API arrays do not establish publication order. A complete DOCX byline, located by the question-subject boundary or explicit motion `Depute` template tags, can reorder the already verified identities using unique exact full names (case, Unicode composition and whitespace normalised), including question political-group annotations and motion group blocks. Partial, unknown or ambiguous names retain every API author in the original fallback order; body prose cannot establish a byline. The response records whether order comes from the published byline, with its source URL and retrieval time, or remains unordered API metadata. Answer views use a saved linked-question byline without downloading a second document; missing ordering evidence never hides an available answer. Saved readable documents remain available while a background read adds missing byline metadata. Individual amendment proposers retain their published `Members` sequence through extraction, identity resolution and per-list display.
- Question addressees come only from explicit `ADDRESSEE` participation and its organisation references in saved source records. Cards show the official question number and supplied recipients; identical titles remain separate questions when their identifiers differ. “Addressed to” scopes results, topic counts, country comparisons, timeline denominators and question/answer text search. Each question counts once per recipient; facet counts respect the other filters and can overlap for multiple recipients. The display label for `org/HRVP` is “Vice-President / High Representative”, shortened from the title used on Parliament’s [public questions page](https://www.europarl.europa.eu/plenary/en/parliamentary-questions.html?tabType=wq). Labels are resolved from exact organisation IDs, including in retained metadata; IDs, URIs and source participation are unchanged. Missing recipients remain “Addressee unavailable”; unfamiliar organisation IDs remain visible. The filter uses exact `org/…` IDs or `unavailable`, and `q-addressee` preserves the selection in page links. Source URLs, retrieval dates and participation IDs remain available in the question response.
- Older website speech references use a hyphenated legacy document number (e.g. `CRE-9-2021-11-24-INT-3-103-0000_EN.html`). No archive-wide changeover date is known.

### Availability of dated records

`server/source-availability.mjs` classifies saved-snapshot evidence by source family, subtype, processing stage and text language. Frontiers ignore person, group, topic and country filters. Checked intervals describe records available in a snapshot, not whether an event-date cohort has finished publishing. Publication maturity remains unknown. Charts keep the selected calendar, break lines at null periods, and mark partial values visibly and in text alternatives. Combined metrics preserve distinct observed records and carry each dependency's state; shares use the same saved record set.

Member activity lists, Questions, EuroVoc trends, Participation, Group voices, Outside voices, speech clouds and contribution statistics share this model. EuroVoc distinguishes EP procedure events from missing Cellar topic mappings; a bounded dossier selection is partial and favours the latest matching event dates. Speech metadata and exact-language readable text have separate frontiers. Language retention exclusions never establish that a translation is unpublished. Finite vote observations, corrections, live-feed expiry, scheduled procedure events, profile periods and local Following discovery marks retain their existing meanings.

The existing leased index and corpus writers retain prospective observation history in their own databases: at most 20,000 exact ID/stage/language/variant observations and 256 completed catalogue checks, retaining event dates and checks from the last 90 days. Source retrieval times and local observation times are separate. Entries describe first retained observations within this bounded history; baseline, backfill, incremental and recovery acquisitions remain distinct. Generation copies create no observations. Successful pagination records requested scope and page retrieval bounds independently of missing detail or text work. Pruning is explicit, and history cannot establish first public availability or a publication SLA. Readers tolerate older databases without this optional history and never create it.

### Speeches and debate structure

The [plenary debates service](https://www.europarl.europa.eu/plenary/en/debates-video.html) publishes speech texts after transcript processing, sometimes out of speaking order. The [minutes and vote results service](https://www.europarl.europa.eu/plenary/en/minutes.html?tab=votes) publishes roll-call annexes separately. Website documents, API records, translations and this site's exact links can become available at different times. Activity dates describe when events took place; retrieval dates and document issue dates do not establish when a speech or vote first became publicly readable. There is no verified API publication deadline.

Agenda messages keep scheduled items, today's schedule, unavailable records and source failures separate. Missing records after a known source frontier say **Not yet available**; otherwise missing links remain explicit. There is no age-based waiting period or promised deadline. Earlier linked debates remain readable, country-filtered emptiness does not imply unpublished speeches, and not every vote has a named roll call.

- Speech headers are in `recorded_in_a_realization_of[].api:xmlFragment.<lang>` under `oralStatements/*/from/process`. Request them with `include-output=xml_fragment`.
- Blue-card questions, answers and reactions share the activity type `PLENARY_DEBATE_SPEECH`. Classify them from the header label, never from speech bodies. A `question` element alone does not identify a blue card. English fragments sometimes keep German labels (`Frage`, `Antwort`, `Reaktion`, `blaue Karte`). Verified complete-label aliases use the XML element as a guard: French answers can become `Blue Carton Response`; Danish, Hungarian and Lithuanian counter-replies can become ambiguous English response labels; Estonian questions can become `Blue Card issue`. Original-language headers, including `mul` fragments, can resolve an absent English header; conflicting original classifications remain unknown. Machine translation can also collapse a Dutch answer and reaction into `Blue Card Response`. For that translated label, `speech` means reaction and `answer` means answer; original English responses retain their own meaning.
- Some oral explanations of vote and chair interventions have no API transcript link even though the published CRE contains their exact speech identifiers, speaker identifiers and recording timestamps. `server/speech-intervention-annotations.json` records verified classifications and public-source URLs, retrieval dates, languages, selectors and hashes. They apply only when the event ID, participant, date, both times and supplied agenda parent match exactly. These annotations do not create API headers, transcript text or relationships. Published document language interfaces can contain the same original text rather than independent translations. Missing chapter exports and inconsistent minutes identifiers do not justify matching by names or changing a published parent.
- Debate order comes from joining `inverse_consists_of` to the parent's `consists_of`, sorted by `numbering`. The API has no reply-to field, so exchanges are derived. Gaps, duplicates or unclassified records stop reconstruction.
- Oral speeches can have contradictory `inverse_consists_of` agenda links. Outside voices and debate sequences narrow these only when all retained speech documents' `is_part_of` evidence identifies one of the published parents by the same term, date and complete CRE/PVCRE item number (including subitems, allowing CRE zero-padding). Missing or conflicting document evidence retains the supplied links; no parent is invented. Older Outside voices projections retained only one document basename: ambiguous rows are re-read once by the existing source writer under its normal budgets, with failed verification retained as a retry gap. Verification stays in the canonical queue across active-generation runs and daily snapshot changes, preserving backoff and pending coverage. Page reads never fetch or rewrite sources. Original links remain available in source details. Debate coverage reports fetched records explicitly resolved to another chapter separately from missing records; unavailable records remain gaps. A resumption is a separate procedural chapter, sometimes containing real speeches; it neither inherits the previous subject nor assigns the next one. Continued debates retain their explicitly numbered chapters. Chair-change and other procedural records keep their supplied containment.
- Catch-the-eye is a `PROCEEDING_ACTIVITY` section with start and end markers (`Catch-the-eye procedure` or, machine-translated, `On-demand interventions`). Other `PROCEEDING_ACTIVITY` records are procedural notes.
- `MEETING_NAME_CHAIR` records name a new chair in `communication/heading/person`, with the role in `communication/subheading`. The person must match the record's participation ID. A debate's `consists_of` sometimes lists such a record twice: by its `PVCRE-CHA-<n>` activity ID and as `MTG-PL-<date>-OTH-<k>`, where `CRE-<term>-<date>-OTH-<k>` is the record's own transcript document identifier. The `OTH` form is not served as an activity, so debate coverage counts it once with the fetched chair record, but only when all of that record's document identifiers, URIs, `notation_speechId` and `is_part_of` term/date agree on the single fragment. Other unserved children remain gaps. Legislation `exactChildReferences` counts raw child references and is not deduplicated this way.
- `had_participation.participation_in_name_of` records speaking capacity for **On behalf of**, not group membership. Match the person and organisation on the same speaking participation. NI is not a political group.
- Plenary “Who is involved” lists people outside the current roster first, then rapporteurs, opinion rapporteurs, shadows and opinion shadows, using each person's highest documented role. Within each rank, political groups follow their size in the saved current MEP roster, with non-attached and unknown memberships last; names and exact IDs break ties. Country filters do not change group sizes. Before the roster is available, group codes provide a stable fallback order. The office label prefers this contribution's requested-language header, then English. A missing translation can reuse the nearest earlier retained speech for the exact person ID only within the same parliamentary term and speaking capacity, with at least one identical shared-language role label and no contradictory shared label. Same-day reuse needs a strictly earlier timestamp. Missing comparison evidence, changed roles and ambiguous chronology leave “Role translation unavailable”. Reuse retains both speech IDs, source URLs, retrieval dates, languages and compared labels; page reads never fetch or write history. Lookups are capped at eight per retained page, each considering at most 512 recent catalogue rows. A truncated day cannot establish the nearest role.
- Search attributions, activity co-authors, amendment proposers, insight people cards, debate labels and speech-cloud examples prefer the directory’s structured given/family names by exact person ID. Unmatched IDs and incomplete directory entries keep their supplied labels without case conversion; changed labels remain available in name tooltips. Source text and evidence retain their original spelling.
- Display names use the roster/profile `givenName`/`familyName` and `officialGivenName`/`officialFamilyName`. The UI prefers a supplied form in its script and never transliterates. A President/Vice-President office requires an exact Parliament membership valid on the speech date.

### Group voices

The group view counts distinct oral speech/person/group designations from `had_participation.participation_in_name_of`, beginning with term 10. Missing designations, untranslated role headers, dated rosters and offices never create a group attribution. Localised names retain the exact person ID.

The activity writer stores a compact, generation-scoped metadata projection with exact participation, organisation, speech and agenda IDs, source URL and retrieval time. A separate optional queue re-reads monthly oral metadata catalogues once when upgrading an old index, under the existing lease, request, time and disk budgets. It preserves core and amendment cursors and does not block core publication. Older application versions ignore the additive tables; the next new writer adopts the last retained projection and pending cursors. Page reads use a group/date covering index, at most 20,000 scalar designations and 50 contribution records, without upstream requests or transcript scans. Coverage stays partial even when the local backfill finishes; an empty selection is not a parliamentary census.

Subjects use the versioned editorial primary-subject map in `server/group-voice-subjects.json`, joined only by exact agenda or speech ID. The map currently covers reviewed July, September and October 2026 headings. These are broad editorial groupings, not EuroVoc or official annotations of individual speeches. Each contribution has one primary subject; unlisted records and conflicting parents stay **Unclassified**. Add classifications by reviewing an exact published heading and updating the map and its version (which queues a bounded metadata re-projection), never by joining titles or assuming an MEP specialises in a topic. Subjects and people show contribution counts, not speaking time or political influence.

### Motions and outcomes

- Outcomes use `/plenary-documents/{id}`, `/meetings/{sitting-id}/vote-results` and `/meetings/{sitting-id}/decisions`, requested with `filter-output=voters` to omit named voters. Documents link to votes through `inverse_based_on_a_realization_of`, and joint motions to their originals through `is_derivative_of`.
- Expanded member activities reuse the member-vote reader for each exact motion or amendment decision ID and its held sitting. Named positions, declared intentions, split descriptions, requesters and tallies follow the same validation as Votes. Links open that exact decision with all positions included; missing named ballots remain distinct from abstention or absence. The indexed outcome remains visible while vote details load or fail; omitted fields retain saved observations, while contradictory records are labelled separately.
- A decision qualifies only if it belongs to the linked vote result, names the same B10/RC-B10 reference in its English heading, and covers the whole motion. Both “Motion for a resolution” and “Motion for a resolution (as a whole)” qualify. All declared decision children must be present. Show-of-hands decisions give an outcome without totals.
- Wording comparison: `/procedures/{id}` lists candidate adopted texts via `created_a_realization_of`, and `/adopted-texts/{id}` must `adopts` the exact joint motion. Both texts must share a published DOCX language.
- Sitting outcomes refresh at most every six hours during the correction window. The [10th-term roll-call annex](https://www.europarl.europa.eu/doceo/document/PV-10-2026-04-30-RCV_EN.html) describes corrections during the two weeks following the part-session. The [Plenary Guide](https://www.europarl.europa.eu/sed/doc/ext/manual/Plenary_guide_en.pdf) gives Friday noon of the second following week as the submission deadline and cites Rule 195 for roll-call voting; the deadline here follows that publication guidance. Confirmation becomes eligible on the later of day 15 after the sitting and that Saturday, adding a calendar safety margin. One complete confirmation then finalises the retained outcome. Missing children, retained/truncated evidence, recorded failures and projection upgrades prevent finality and retain bounded retries. Corrections do not alter the announced vote outcome. This policy concerns the background activity/amendment index; selected-period member-vote reads retain their independent source coverage.

### Plenary amendments

Amendment trails for reports and motions are collected by the activity-index worker in a separate job queue under the same writer lease. Reads never fetch sources (`server/amendments*.mjs`).

- `/plenary-documents/{id}` lists amendment-list documents through `inverse_foresees_change_of`. Each list must `foresees_change_of` the target. When the link is URI-only or the record incomplete, `/documents/{doc-id}` must confirm the URI, amendment-list type and forward target.
- Each list's API-linked DOCX supplies amendment numbers, proposers, group statements, target provisions and the original/proposed columns. When the table structure is ambiguous, both wording columns are withheld rather than guessed (`server/amendment-documents.mjs`).
- Outcomes come from the sitting `/vote-results` and `/decisions?filter-output=voters` records shared with motion outcomes, through `decided_on_a_realization_of`. Split votes keep separate component outcomes. A missing outcome is unavailable, never a rejection.
- Author links need an exact normalized full name or an official voting alias, plus an active mandate on the tabling date from the dated roster. Aliases come from the roll-call XML of `/plenary-session-documents/PV-10-{date}-RCV`, where `PersId` is the Open Data person ID and `MepId` is a different identifier. Ambiguous identities stay unlinked.
- Split-vote descriptions are parsed from English (`server/amendment-splits.mjs`). A parsed plan has `grounding: not_attempted`: it does not establish a validated wording span or the final adopted text. Unparsed descriptions are recorded, exposed read-only at `/api/amendments/failures`, and reparsed when the parser version changes.

The context-specific `/api/motion-amendments/{id}` endpoint reads those indexed observations for one exact original or joint motion. Text authorship comes only from that text's exact `creator` or person participation with role `AUTHOR`; original/joint links require `is_derivative_of` and do not transfer authorship. Selected-member amendment matches use the checked proposer date and resolved identities independently, including per-list variants. All-results annotation, member filtering and exact amendment selection share the same checked read rules. An exact primary or observed official amendment identity can be selected outside the current page or member scope; an ambiguous or missing identity remains unavailable.

Whole-motion outcomes use the separately indexed sitting result/decision relationships and exact whole-text references, including decisions without a named roll call or numerical totals. They never derive from amendment results, vote totals or selected-member intention. These motion sources provide no named member position. Conflicting indexed decision references withhold the result; disputed totals are withheld separately. An adopted-text relationship requires its own exact `TEXT_ADOPTED` metadata and explicit `adopts` reference to the queried motion. The current index does not generally collect those adopted records, so missing relationships remain unavailable. This read API neither discovers them upstream nor replaces missing original wording with adopted text.

The wording views compare only the original and proposed text of the same published variant, in its recorded wording language. Highlights are computed locally with a bounded, lossless token diff; lengthy or extensively changed passages fall back to unhighlighted columns. Empty wording is treated as an insertion or deletion only where the source projection supports that meaning. These comparisons do not reconstruct adopted text; the official document is authoritative.

Comparison headings retain both raw labels and exact language-specific categories (`commission-proposal`, `present-text`, `council-position`, `motion-resolution`, `other`, `unknown`). The vocabulary is backed by public DOCX excerpts in all 24 languages; unrecognised labels stay unknown and differing table categories remain conflicting. Structured DocRef/DocAmend references and separate proposal/underlying-act target paths retain raw labels and source provenance. Earlier parser versions remain unknown until the existing source writer refreshes them.

List number ranges do not establish the presence of every number. Revised or conflicting lists retain their separate wording and proposer evidence; ambiguous aggregate wording is withheld. Requested language, actual amendment wording language and queried-text file fallback are separate observations. Whole-amendment outcomes remain separate from split decisions, including mixed, lapsed, withdrawn and unavailable results. Adoption alone establishes neither causal credit nor wording survival. The endpoint preserves source URLs, retrieval dates, parser and distribution freshness, and retained evidence after partial refreshes. An empty unindexed target is unavailable evidence, not no amendments. An explicitly empty current list relationship has its own source proof and narrow `published-amendment-list-relationships` observation scope; it cannot erase retained records or establish absence of oral amendments or complete vote evidence. Global background work does not establish that this target is being processed.

### Documents (DOCX)

Distributions linked by the API are processed locally with bounded decompression (`server/document-text.mjs`). Extraction reads `word/document.xml` plus style, numbering, settings, footnote and endnote parts. It omits deleted/moved-from text and effective `w:vanish` or `w:webHidden`, including inherited/default styles and direct overrides; inserted/moved-to text remains visible. Automatic numbering, referenced notes, links and literal braces/angles are retained. The shared reader and amendment extractor continue counters across concrete instances of the same abstract list; explicit start overrides restart a level on first use. Level restarts follow [Word's documented rules](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/140a2cd9-2f26-456d-9760-ae6ecef4e8b5), including higher-level triggers. Literal paragraph labels remain unchanged. Page-dependent note restarts and unsupported numbering are explicit gaps. Answer PDFs carry the same link targets as their DOCX, so only DOCX is read.

Known `w:sym` font/code pairs are converted mechanically: Symbol `F02D`/`002D` becomes U+2212 MINUS SIGN using the [Adobe Symbol mapping](https://www.unicode.org/Public/MAPPINGS/VENDORS/ADOBE/symbol.txt) and [Microsoft's legacy symbol-font offset](https://learn.microsoft.com/en-us/typography/opentype/spec/recom#non-standard-symbol-fonts). Other symbols, drawings, equations and unsupported inline objects retain an object replacement character (U+FFFC), source position and metadata without discarding surrounding text. Their paragraphs have `complete:false`; a leading known symbol does not make its paragraph incomplete.

`paragraphs` remains a string array. `paragraphSources` aligns with it and supplies indexed XML `path`, zero-based source paragraph `ordinal`, `container`/`containerPath`, continuity `segment` and `complete`. Matching across paragraphs requires complete text, the same container and segment, and consecutive ordinals. Omitted paragraphs, unsupported blocks, tables and cell transitions interrupt continuity. When skipped content may consume list items or note references, later affected automatic labels are `?` with a warning and incomplete paragraph metadata. `documentObjects` locates mapped/unresolved objects by paragraph and UTF-16 offset. `structureStatus:not-extracted` means boundaries are unknown; legacy records never receive inferred structure. Reader responses also expose `extractionVersion` and `sourceVersion` (the API listing's `byteSize` and `issued`, distinct from downloaded byte length).

Presentation is recorded beside the unchanged text (`server/docx-formatting.mjs`). `paragraphFormats` aligns with `paragraphs` and gives alignment, left/hanging/first-line indents in em at the body text size, heading level from `w:outlineLvl`, a relative size class, and bold, italic, underline, strike, superscript and subscript spans as UTF-16 offsets; style inheritance follows `basedOn`, toggles combine across paragraph and character styles, and direct run properties win. `tables` lays out outermost tables as exact paragraph ranges per cell, with grid spans, vertical merges and whether any cell keeps visible borders; nested tables stay inside their cell. `formatStatus:not-extracted` means presentation is unknown and readers show plain paragraphs. Texts saved before formatting was recorded remain readable and are re-read in the background when opened.

Extracted texts are saved in `ODP_CACHE_DIR/document-text-v1` with source URL, retrieval time, extraction version and the API's file size and issue time. An older extraction version is replaced only when the document is opened; a failed upgrade retains the disk record and reports text unavailable under the current parser. Cold reads propagate typed local admission/deadline failures so API callers can return retryable errors; a failed background refresh still serves retained text. Distributions send no HTTP validators, so the API listing is the change signal: a different size or issue time re-reads the file. Otherwise a text retrieved within 60 days of its document date is re-read at most weekly when viewed, and a text retrieved later is kept. The directory is capped by `DOCUMENT_TEXT_MAX_DISK_MIB` (default 256) and removes the least recently read texts first; a removed text is downloaded again when next opened.

Proposal parsing reuses bounded DOCX extraction and adds ordered provision paths, replacement scopes, structured table cells and safe MathML objects. It retains memorandum and financial-statement content separately from the legal body, supports all 24 official-language label grammars, and keeps unsupported objects and duplicate targets explicit. The proposal-only numbering resolver continues shared abstract lists with explicit restart overrides; the general document reader keeps its existing default. See [Proposal structure](PROPOSAL_STRUCTURE.md) for the interface, matching policy, completeness and cache rules. This parser does not fetch or select proposal baselines.

### OEIL

Summaries are parsed from visible HTML, reached through the exact procedure reference from the API. Final-act summaries are preferred over proposal summaries. No summary is invented when none is published.

### Press releases

The activity-index writer reads Parliament's English RSS feeds for [press releases](https://www.europarl.europa.eu/rss/doc/press-releases/en.xml), [plenary](https://www.europarl.europa.eu/rss/doc/press-releases-plenary/en.xml) and [committee](https://www.europarl.europa.eu/rss/doc/press-releases-committees/en.xml) press releases once a day (`server/press-releases.mjs`, `server/press-releases-model.mjs`). Each feed holds only its latest 20 releases and carries no procedure or document references. Coverage therefore starts when following starts, and releases that leave the feeds between reads are missing. Following data accumulates in `press-v1.sqlite` in the index directory and is not rebuilt with index generations.

Releases are discovered only through these feeds. Each announced release's English page is read once; press-room listings and search are never crawled, and links on a page are never followed. Parliament's robots.txt does not disallow `/rss/` or `/news/`. Only exact links in the page's own “Further information” list count: OEIL `procedure-file?reference=…` (encoded slashes and stray spaces are normalized), OEIL `document-summary?id=…`, and Doceo reports, motions, adopted texts and committee drafts (`A`, `B`, `RC`, `TA`, `PR`, `AD`, `AM`, `AL`, `PA`). Minutes, agendas and verbatim reports cover many files and are ignored. A summary or document link matches a dossier only when that dossier's OEIL procedure file links the same ID. Links in body text are context mentions. Titles, committees and topics never establish a link. Pages whose robots meta tags or `X-Robots-Tag` header say `noindex`, `nofollow` or `none` are neither shown nor used. Reads use the website admission pool, the browser-compatible user agent and the worker's request budget and deadline: at most six pages per worker iteration, 2 MiB per page. While index work is also due, press reads take a tenth of the budget, or one request every other iteration when the budget is below ten; this alternation resets when the worker restarts. Each feed's releases and status commit together, so an interrupted poll resumes with the remaining feeds. Writes hold the activity-index lease until they commit; readers never create the store.

The committee “latest news” feed is not followed: its highlight pages carry `noindex, nofollow` and no procedure or document links. Plenary newsletter items have no feed of their own.

`GET /api/insights/press-releases?reference=…&lang=…` returns the latest five matching releases with English titles and source URLs, the total found, and coverage: the following start, each feed's last success and error, whether the procedure file's summaries and documents could be checked, and whether that saved page is stale or failing to refresh, and counts of pending, unreadable and unlisted releases. `complete` is always false. The dossier reader shows up to three releases under agenda items and five in the Dossiers view, and nothing when none were found.

### Publications Office

Commission proposal baselines are available to the internal `proposalBaseline({reportId, celex, language, documentReferences})` source function (`server/proposal-baseline.mjs`). A report's explicit COM and COD references must agree with its procedure relationship. Exact COM candidates and the CELEX tree must establish one Commission-authored proposal, final version and matching dossier. Corrigenda, amended/competing versions, missing references or conflicting identities remain unresolved. Same-language expressions, DOCX manifestations and every act/annex part are discovered through RDF identities and explicit aliases; suffixes are never constructed. Missing languages and formats remain unavailable. The returned DOCX buffers use the existing bounded DOCX pipeline. For a selected `commission-proposal` amendment, `/api/document-context` reads the proposal in the exact wording language, returns its act and annex projections with source identity/attribution, and resolves the proposal-level target. Present-text, Council-position and unknown baselines remain unresolved. Original wording must match one complete unit or one unique contiguous source slice; insertion labels must identify one preceding sibling and an existing parent. The app-generated diff preserves source notes and links and is identified as unofficial. Projection responses are capped at 3 MiB and reuse the bounded context and parser caches; partial or stale baselines do not acquire a fresh context TTL.

CELLAR uses `application/rdf+xml;notice=tree` for metadata and `application/vnd.openxmlformats-officedocument.wordprocessingml.document.main+xml` for DOCX. Upstream HTML is never served. Only validated `publications.europa.eu/resource/celex/…` and discovered CELLAR UUID paths are fetched. At most three same-host redirects are followed, upgrading validated HTTP Locations to HTTPS. Each operation uses the shared Publications Office origin queue and a 20-second admission/redirect/body deadline; one baseline read has a 45-second owner budget. Metadata is capped at 3 MiB, DOCX at 8 MiB per part (the existing reader limit), 24 MiB per bundle and 32 parts. Source throttling uses the origin queue's Retry-After pause.

Metadata expires after six hours. Viewed content is conditionally revalidated after seven days with ETag/Last-Modified. A SHA-256 blob cache outside Git (`ODP_CACHE_DIR/commission-proposals-v1`) has a 256 MiB disk budget and 24 MiB memory budget; identity/language/item/format records retain validators and retrieval/check dates. Failed or malformed refreshes retain the last valid source with stale/error gaps. A valid partial source is never labelled complete. Content hashes and exact RDF identifiers are returned for downstream parsing and mapping.

Proposal text retains the Commission/Publications Office source, language, version and original-file URL. Reuse follows the [EUR-Lex legal notice](https://eur-lex.europa.eu/content/legal-notice/legal-notice.html?locale=en) and document-specific third-party exceptions; Cellar metadata is CC0 under its [legal notice](https://op.europa.eu/en/web/cellar/legal-notice). Any derived diff must identify its modifications and must not be presented as an official consolidated text.

- Legislative progress loads independently from OEIL through `/api/insights/procedure-progress?reference=…&lang=…`; `detail=documents` is requested only after a reader opens an event's documents. Exact procedure references, including split suffixes, map to a single Cellar dossier. Unmatched or ambiguous mappings leave Parliament content available. Up to 300 distinct event identifiers are retained, within 1,201 event rows or 2,401 document rows; caps, malformed rows and missing/conflicting event fields remain explicit. Scheduled events stay scheduled after their date passes; future dates with no supplied status are not treated as completed actions. Council events never alter Parliament activity counts.
- Progress reuses the single official-source client, per-origin admission queue and bounded memory/disk cache. Responses are validated before caching; malformed refreshes retain the last valid observation. Viewed progress expires after one hour and refreshes in the background; saved records retain their source retrieval date and refresh errors. Saved document details can be checked again or refreshed by reopening their disclosure, retaining visible content during the read. There is no preload or additional writer. Source requests have a 20-second deadline, same-origin HTTPS redirects and a 3 MiB JSON limit. Fresh, complete progress responses have browser `max-age=0` and a five-minute CDN lifetime; partial, ambiguous, stale or failed responses are not publicly cached.
- Event-linked document works resolve only through exact CELEX identifiers. Reader links open EUR-Lex text using the available title language with an explicit fallback. Capped document responses retain metadata but withhold links because identifiers may be incomplete. Council metadata aliases do not establish a publicly available PDF; unsupported or conflicting identifiers do not create links. Raw graph/query URLs and Cellar resource identifiers remain in response provenance, not reader links; the existing site footer supplies general attribution. No legal-effect graph or generic entry-into-force date is inferred from these events.
- Legal references in questions and answers (CELEX, ELI, Cellar, COM/SWD/JOIN, procedure and question numbers) become lookup keys through fixed patterns and are resolved in batched SPARQL. A reference links only when exactly one work matches. Official Journal position links (`uri=uriserv:OJ…`) are not resolved.
- `src/terms.json` holds procedure-phase labels (RDG1, RDG2) in all 24 languages, with concept URIs and query provenance. IATE entries corroborate them but are not substituted.
- **Vote**, **Amendment** and some short interface labels are app-owned machine translations with model/date provenance. They are not official translations. EuroVoc 4750 (electoral voting) gives the wrong sense for parliamentary votes.

### Live plenary

`GET /api/plenary-live` reads the current Brussels day's [plenary JSON feed](https://www.europarl.europa.eu/plenary/en/getSpeakerListAndPlenaryMessages.html?dateSys=20261020), Open Data `/meetings/{sitting-id}/foreseen-activities`, and the [EbS+ current-programme JSON](https://8hwk2cyeyb.execute-api.eu-west-1.amazonaws.com/parrotfish-prod/ebs/live/EBSPLUS). These are anonymous machine reads: there is no HTML-page scraping, catalogue crawl, daily manual mapping or hardcoded event URL. The two website JSON interfaces are undocumented and have no published availability guarantee. Failures remain separate source gaps. Requests share the existing admission queues, with a 512 KiB body bound, eight-second website deadlines, a twelve-second shared owner and a thirty-second memory snapshot. Browsers poll while visible, or while the player is open, never cache the response at the CDN, and expire status after 75 seconds without a successful observation.

The plenary feed's `D…` debate IDs are a different namespace from Open Data's `…OJ-ITM-D-…` IDs. The current debate is displayed with its source title and source update time; no title-based join is made. Only today's source updates within three minutes qualify. Agenda markers say **Scheduled now** and require one timed `MEETING_PART` with one exact agenda child. Several children, overlapping blocks or conflicting end times retain ambiguity. Timetables never prove that an item is actually being debated, and missing live observations do not prove a recess or an ended sitting.

EbS+ playback uses the broadcaster's generated embed `https://audiovisual.ec.europa.eu/embed/ebsplus?language=EN`. Programme selection requires `PUBLISHED`, `LIVE`, the exact EbS+ channel ID `6082c9bb97ad8b2acf7fcc98`, today's started programme, English audio, published unlocked material attributed to European Parliament institution `2618`, and the broadcaster's explicit first title paragraph `EP Plenary Session`. This is a documented programme classification, not an agenda join. Other EP coverage, recorded footage and unknown classifications do not expose a plenary player. The metadata timestamp is an editorial update, not a heartbeat. Playback may lag the source's current-debate indication; users can use the player’s Live control. The iframe is created after Watch and remains mounted while browsing or minimising; closing it, a fresh observation without a live plenary programme, or two further minutes without any observation removes it. That grace covers background tabs, whose timers browsers throttle to about once a minute; the banner and agenda markers still expire at 75 seconds. Pop out opens the same allowlisted embed in its own window, without an opener reference to the explorer, and closes the inline player; a blocked popup leaves the inline player in place; that window is the broadcaster's page and no longer follows our status checks. The player also links to the [EP Multimedia Centre](https://multimedia.europarl.europa.eu/en/webstreaming) live listing. Interpretation controls belong to the official player. Use follows the [Audiovisual Service conditions](https://audiovisual.ec.europa.eu/en/conditions-of-use); attribution is shown beside playback. No video is downloaded or proxied.

### Multimedia Centre and player

Videos play in the Parliament's own embedded player. The Multimedia Centre website offers embed URLs for its recordings, and we use the same official embed (`https://webstreaming.europarl.europa.eu/ep/embed/embed.html?event={recording-id}`). The only difference is that we look the URL up programmatically instead of copying it from the website (`server/mmc.mjs`):

1. The recording's metadata, including that embed URL and the recording's start and end times, comes from `https://api.multimedia.europarl.europa.eu/o/epmp-frontend-rest/v1.0/media/{recording-id}`, the endpoint the Multimedia Centre website itself calls.
2. A speech's start and end times from the Open Data API select exactly one recording. The embed URL gets the player's own `start`, `end`, `language` and `audio` parameters, so it opens at that speech.
3. Before playback, the player's metadata connection confirms that the requested interpretation track exists: `wss://websockets.services.eup.glcloud.eu/content-manager/api/v1/socket.io/?EIO=4&transport=websocket`, namespace `/content`, event `join:event`, with the recording's public `commonId` (`server/player-content.mjs`). Only `PUBLISHED` content matching the recording is accepted. The embed starts paused on the original audio (`audio=or`). The client then checks the iframe's actual track list and adaptation events before switching to the requested language, and does not play if that selection fails or is ambiguous.

Both endpoints are undocumented and may change. The server reads metadata only and never downloads video. The [Multimedia API robots policy](https://api.multimedia.europarl.europa.eu/robots.txt) disallows crawling outside `/documents/`; the adapter performs exact-ID metadata reads and does not crawl or automatically search the recording catalogue. Speech-to-recording lookups use a saved catalogue of public Multimedia Centre search results, and missing coverage is shown.

### Portraits

The API supplies portrait URLs. Each MEP record's `img` field points to the website image, e.g. `https://www.europarl.europa.eu/mepphoto/4465.jpg`. The images themselves are hosted on the website, not served by the API. If `img` is missing, the same URL pattern is built from the MEP ID. Only that path pattern is accepted. Images are fetched on demand through `/api/portrait/{id}` and cached in `ODP_CACHE_DIR/portraits-v1` with source URL, retrieval time, checksum and the host's `ETag`/`Last-Modified` validators (`server/portrait-cache.mjs`). Portrait downloads and saved-image reads accept JPEG bodies up to 8 MiB; retained memory stays capped at 8 MiB and disk storage at 1.4 GB (1,400,000,000 bytes), with bounded entry counts. The roster is never prefetched. A portrait viewed more than 7 days after retrieval is refreshed in the background with a conditional request; a `304 Not Modified` keeps the saved image and records the confirmation as the new retrieval time. The Open Data API and the other periodically read sources (activity RSS, Multimedia Centre, OEIL, Publications Office SPARQL) send no validators, so they are re-read on their cache lifetimes.

## Full-text corpus

With `CORPUS_ENABLED=true`, a leased worker stores current-term texts in `corpus-v1.sqlite` (`server/corpus-worker.mjs`, `server/corpus-store.mjs`):

- Speeches come from `/speeches` with `include-output=xml_fragment`, month by month. Fragments marked `mtec` are machine translations. Recent months are rechecked because translations arrive later. Readers preserve the XML’s `<inline name="i">` italics in place, including editorial remarks within paragraphs and between speech paragraphs. Parentheses alone do not identify editorial remarks.
- Question and answer texts come from the DOCX distributions of saved index records. Original languages and English come first. `CORPUS_LANGUAGES=primary` keeps only those.

Search uses SQLite FTS5 with Unicode tokenisation. Latin diacritics are folded, Greek accents are not. Endpoints:

- `GET`/`POST /api/corpus/search` search retained text only. POST accepts exact `sourceIds` scopes. The `addressee` option (GET query or POST body) matches the saved parent question’s explicit recipient before grouping or paging, including when only its answer text matches. It requires a serving activity-index generation and saved parent-question metadata for otherwise matching texts. Missing parent records make the filtered selection unavailable; they do not enter the “Addressee unavailable” bucket, which describes saved questions without supplied recipients. Search never downloads metadata. Omission or POST `null` leaves the scope unchanged; an empty string is invalid. Results are grouped by document by default. With `group=question`, a question and its linked answers count as one group. `total`, `offset` and `nextOffset` count groups. Clients must follow `nextOffset`, because `responseLimited` pages can be shorter than `limit`. Pagination stops at offset 1,000 (`truncated: true` means more matches exist; narrow the filters). Queries run one at a time in read-only workers, and busy or slow queries return HTTP 503.
- `GET /api/corpus/text?source-id=…&source-key=…` returns one stored variant with provenance, optionally highlighted with `q`.
- `GET /api/speech-transcript/{id}?lang=…` reads the exact retained speech language and its compressed XML, with source key, translation type and retrieval provenance. The corpus writer also retains the full official metadata once per speech, without duplicating XML, and derives speaker/header and intervention projections from supplied or retained fragments. Header projections include translations excluded by the text retention policy; metadata-only refreshes retain known speaker-name variants for exact current participants. Readers use that metadata and cached person records without upstream calls. Metadata retrieval and header/text provenance remain separate. Missing corpus languages or metadata use the existing speech-detail fallback; metadata delays and errors cannot block retained text. The read-only transcript workers have a separate concurrency limit from full-text searches, and page reads never create a corpus or start collection.
- `GET /api/corpus/status` reports coverage. Cold count scans have a bounded 6.5-second reader budget (searches retain 5 seconds); a timeout returns HTTP 503 `corpus_status_timeout` and means coverage is unknown, not zero. Retry shortly. Counts remain live snapshot observations rather than cached totals. `authoritativeComplete` is always false, because upstream gaps and later publications rule out a completeness claim.

Older corpora gain metadata through the existing leased writer: a resumable, metadata-only monthly catalogue backfill, including missing-record recovery, uses the same request, retry, time and disk budgets and does not redownload transcript XML. A versioned local task refreshes unresolved contribution classifications from retained XML and verified public-source annotations, without source requests or changed retrieval timestamps; status exposes pending refreshes and failures. New and refreshed speech pages retain metadata during normal ingestion. Compact header projections preserve classification evidence even when a fragment has no paragraph text. Individual metadata failures become separate retry tasks, so text ingestion and monthly cursors can continue; status keeps those gaps visible. Known source languages remain available in the picker independently of which variants the corpus retains; selecting a variant absent from the corpus uses the detail fallback. Metadata-only refreshes preserve that known availability. `/api/corpus/status` reports retained metadata and whether that backfill is pending; source gaps remain explicit.

Speech clouds and contribution statistics prefer bounded pages from the retained speech corpus. Their totals describe saved records; a finished backfill does not establish an authoritative catalogue. The contribution card labels the latest saved speech record across the collection and warns about known missing records or unclassified contributions, rather than treating retained data alone as a gap. The existing writer builds a small local selection index from saved metadata without source requests. Clouds use exact-language paragraph text without decompressing XML, preserving translation and retrieval provenance. An absent corpus, unfinished local projection, empty stored selection, or known source language excluded by text retention uses the existing public-source cloud pagination. A selection never mixes local and upstream offsets. Changes to matching retained records restart the page walk; metadata and its selection fields update atomically. Saved word analysis also uses corpus paragraphs first, retaining its saved-file fallback without downloads.

Exact-ID speech context, media lookup, legacy speech readers and legislation associations reuse retained metadata where available. Context uses the saved intervention projection rather than reclassifying metadata with its XML removed. Whole-sitting context still uses the broader source feed: the corpus does not retain all procedural markers. Legislation records already in the activity index are read there first when the saved fields support the requested relationships; incomplete procedure projections retain the source fallback. Document readers retain their existing structured DOCX cache because corpus paragraph text cannot replace notes and links; official source readers continue to distinguish source records from derived projections.

## Test fixtures

`server/fixtures` holds small public API responses and OEIL pages used by tests. JSON fixtures record their own source URLs and retrieval times. OEIL HTML fixtures are named after their exact procedure or summary reference. Fixtures are not runtime catalogues and their counts are not live figures.
